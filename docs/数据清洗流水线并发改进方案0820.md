# 数据清洗流水线并发改进方案

## 1. 背景与目标

当前清洗流水线具备 Manifest、Operator DAG、cache 和断点续跑能力，但
`PipelineRunner._run_step()` 对每个普通 Operator 仍采用单线程逐样本执行。数据达到
10 万～20 万条后，PCM 转换、重采样、probe 等步骤会成为主要耗时。

本方案目标：

- 单机优先，在不改变现有 Operator 业务逻辑的前提下实现并发。
- 保持样本顺序、Manifest 血缘、cache key 和失败隔离语义不变。
- 支持断点续跑，进程异常后只重跑未完成部分。
- 后续可通过 Manifest 分片扩展到多进程、多机或任务调度平台。
- 并发度可配置，避免机械地开满 CPU 导致磁盘抖动或内存耗尽。

## 2. 当前实现的主要瓶颈与风险

### 2.1 普通 Operator 串行执行

当前每一步都是：

```text
步骤 1：依次处理全部样本
  ↓
步骤 2：依次处理全部样本
  ↓
步骤 3：依次处理全部样本
```

样本之间通常没有依赖，适合在“单个步骤内部”并发。`quality.select`、`ingest.scan`
等 `ManifestOperator` 操作整个集合，应继续串行执行。

### 2.2 不能直接给现有循环套线程池

并发前必须处理以下问题：

1. `data/cache/<operator>/<key>.json` 目前直接覆盖写入，并发或进程中断可能留下半个
   JSON 文件。
2. 派生音频目前使用 `<sample.id>.wav`；不同目录中存在同名文件时会互相覆盖。
3. 20 万条样本如果一次性提交为 Future，会产生较大的调度和内存开销。
4. 多线程中直接修改全局 metrics 会产生竞争；应由主线程汇总结果。
5. 音频解码与重采样会同时占用 CPU、内存与磁盘，worker 并非越多越快。
6. 多进程模式下 Operator、Sample 和配置必须可序列化，Windows 还必须使用安全的
   `spawn` 入口。

## 3. 推荐总体架构

采用“两级并发、分阶段落地”：

```text
输入 Manifest
  │
  ├─ 按步骤执行 DAG（步骤之间仍保持顺序）
  │    ├─ ManifestOperator：主进程串行
  │    └─ BaseOperator：有界 worker pool 并发处理样本
  │
  ├─ 每完成一个批次写 checkpoint
  │
  └─ 输出最终 Manifest

大规模扩展：
输入 Manifest → N 个稳定分片 → N 个独立 shard pipeline → 校验并合并 Manifest
```

第一层是单个 Pipeline 进程内的步骤级并发，改造成本低，适合单机 10 万～20 万条。
第二层是 Manifest 分片并行，每个分片有独立 run 目录和 checkpoint，适合多进程或多机。

不建议一开始让每个样本完整跑完所有步骤的“样本级流水线”。当前步骤间会更新
Manifest 字段和 cache，按步骤设置不同并发度更容易控制资源，也能保持现有语义。

## 4. 第一阶段：单机有界并发

### 4.1 新增执行配置

建议在 Pipeline YAML 中新增：

```yaml
execution:
  executor: thread          # thread | process | sequential
  workers: 8                # 默认并发数
  max_in_flight: 32         # 同时在执行或排队的任务数
  checkpoint_every: 1000    # 每完成多少条保存一次 checkpoint
  fail_fast: false
  preserve_order: true

pipeline:
  - name: pcm_convert
    operator: audio.pcm_to_wav
    execution:
      workers: 8

  - name: resample
    operator: audio.resample
    execution:
      workers: 4

  - name: probe
    operator: quality.probe
    execution:
      workers: 16

  - name: audio_pass
    operator: quality.filter
    execution:
      workers: 16

  - name: select_pass
    operator: quality.select  # ManifestOperator，忽略 worker 配置，保持串行
```

优先支持 Pipeline 全局默认值和 step 覆盖值。CLI 再提供临时覆盖：

```bash
audio-data pipeline run pipelines/data_cleaning_source_A.yaml \
  --workers 8 \
  --executor thread
```

### 4.2 为什么第一版优先线程池

当前 `soundfile`、NumPy、SciPy 的主要计算位于原生代码中，很多操作会释放 GIL；
音频读取和写入也包含 I/O 等待。因此线程池可以在较小改造成本下取得明显收益，并且：

- 不需要反复序列化完整 `Sample`。
- cache、日志和 Operator 注册表继续位于同一进程。
- Windows 下无需承担多进程 `spawn` 的高启动成本。

线程池并不保证 CPU 密集步骤线性加速。基准测试若表明重采样受 GIL/CPU 限制，
再为指定步骤启用 `process`，而不是默认全部使用多进程。

### 4.3 有界提交与顺序恢复

不能一次提交 20 万个 Future。Runner 应只维持 `max_in_flight` 个任务：

1. 主线程按原 Manifest 顺序提交任务，并记录 `index`。
2. worker 返回 `index + OperatorResult` 或 `index + 异常信息`。
3. 主线程消费完成结果、更新 metrics，并持续补充新任务。
4. 结果写入预分配列表的原 index，保证最终 Manifest 顺序不变。
5. 单条失败沿用现有逻辑：复制 Sample、写入 failed 状态，不影响其他任务。

建议为 `PipelineRunner` 增加统一的 `_process_one()`，串行与并发路径共用异常处理，
避免两套执行语义逐渐不一致。

## 5. 并发写入安全改造

### 5.1 cache 原子写入

缓存应采用“同目录临时文件 + 原子替换”：

```text
写入 <cache_key>.<pid>.<uuid>.tmp
  → flush（必要时 fsync）
  → os.replace(tmp, <cache_key>.json)
```

这样另一个 worker 只能看到完整旧文件或完整新文件。相同 cache key 被重复计算时，
允许最后一个完整结果覆盖，因为 Operator 应满足相同输入与参数产生相同结果。

如果未来存在昂贵的模型推理，可增加 cache-key 文件锁，避免相同任务重复计算；第一版
无需引入全局锁，以免降低吞吐量。

### 5.2 派生文件唯一命名

将：

```text
data/derived/resample_16k/<sample.id>.wav
```

改为至少包含内容哈希：

```text
data/derived/resample_16k/<sha256前2位>/<sha256>_<sample.id>.wav
```

PCM 转 WAV、重采样、降噪和数据增强 Operator 都应遵循同一命名函数。分两级目录还可
避免单目录下出现 20 万文件导致文件系统访问变慢。

派生文件也应先写临时路径，成功关闭后再 `os.replace` 到目标路径，避免中断后将半成品
误认为有效结果。

### 5.3 日志与指标

- worker 只返回结构化状态，不直接修改 `RunMetrics`。
- 主线程统一累计 `processed/cache_hits/skipped/failed`。
- 进度日志按“已完成数”输出，而不是按提交数输出。
- 每个步骤记录耗时、吞吐量、平均音频时长、失败率和峰值并发数。

## 6. Checkpoint 与断点续跑

现有 cache 能避免 Operator 重算，但如果运行中断，Runner 仍需重新加载原 Manifest，
逐步骤检查全部样本。建议增加步骤和批次 checkpoint：

```text
runs/<run_id>/
  config.yaml
  metrics.json
  checkpoints/
    00_pcm_convert/
      part-000000.parquet
      part-000001.parquet
      _state.json
    01_resample/
      ...
```

`_state.json` 至少记录：

- pipeline 配置摘要和 Operator 版本。
- 输入 Manifest 摘要。
- 已完成的样本数或 shard/part 编号。
- 成功、失败、cache hit 数。
- checkpoint 是否完整提交。

恢复时只采用标记为完整的 part；临时文件和未提交 part 直接忽略。配置摘要或 Operator
版本变化时，不复用不兼容 checkpoint，但底层 cache 仍可按 cache key 判断是否复用。

第一版可每 1000 条写一个 checkpoint。若单条音频很短，可调到 5000；若单条耗时很长，
可调到 100～500。

## 7. 第二阶段：Manifest 分片并行

单机线程池稳定后，增加以下命令：

```bash
audio-data manifest shard datasets/batches/batch_A/manifest.parquet \
  --shards 16 \
  --output-dir datasets/shards/source_A

audio-data pipeline run-shards pipelines/data_cleaning_source_A.yaml \
  --shard-dir datasets/shards/source_A \
  --parallel-shards 4

audio-data manifest merge runs/<run_id>/shards/*/manifest.parquet \
  --output datasets/manifests/cleaned_source_A.parquet
```

### 7.1 分片规则

采用稳定哈希，而不是按当前行号切分：

```text
shard_id = int(sha256[:16], 16) % shard_count
```

优点：

- 同一文件每次都进入相同分片，方便重跑和增量处理。
- 各分片数量通常较均衡。
- 输入 Manifest 顺序变化不会导致全部重新分片。

如果音频时长差异很大，仅按条数可能负载不均。可提供 `strategy: duration-balanced`，
按累计音频时长平衡分片；没有 duration 时回退到稳定哈希。

### 7.2 分片隔离与合并校验

每个 shard 使用独立：

- run 目录。
- checkpoint 目录。
- metrics 文件。
- 临时输出目录。

cache 和最终派生文件可以共享，但必须先完成第 5 节的原子写入和唯一命名改造。

合并前必须校验：

- 所有预期 shard 均成功结束。
- `(source_id, sha256)` 不重复；若重复，按明确规则去重并报告。
- 输出总数 = 各 shard 输出数之和。
- 配置摘要、Operator 版本和 schema 一致。
- 合并后按原始 index 或稳定键恢复确定性顺序。

## 8. 资源控制建议

初始值不要按 20 万条数据量决定，而应按机器资源和单条音频大小决定：

| 步骤 | 主要资源 | 建议初始 workers |
| --- | --- | ---: |
| `audio.pcm_to_wav` | 磁盘读写 | 4～8 |
| `audio.resample` | CPU + 内存 + 磁盘 | `min(物理核数, 4～8)` |
| `quality.probe` | 小文件 I/O | 8～16 |
| `quality.filter` | 轻量 CPU | 8～16 |

额外约束：

- 使用机械硬盘或网络盘时，从 2～4 workers 开始。
- 使用本地 NVMe 时，可逐步提高到 8～16，观察吞吐是否继续增长。
- `max_in_flight` 建议为 workers 的 2～4 倍。
- NumPy/SciPy 底层线程数建议固定为 1，避免“worker 数 × BLAS 线程数”过度并发：
  `OMP_NUM_THREADS=1`、`MKL_NUM_THREADS=1`。
- 单条音频解码会占用与音频长度相关的内存；应通过压力测试设定并发上限，不能只看 CPU。

Windows PowerShell 示例：

```powershell
$env:OMP_NUM_THREADS = "1"
$env:MKL_NUM_THREADS = "1"
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --workers 8
```

## 9. 推荐实施顺序

### P0：并发正确性基础

1. 提取统一派生文件命名函数，引入 `sha256` 分目录。
2. cache 和派生音频改为临时文件原子替换。
3. 为同名 `sample.id`、相同 cache key 并发写、处理中断残留增加测试。

### P1：单进程线程池

1. 为 `PipelineConfig` 和 `PipelineStep` 增加 execution 配置。
2. `BaseOperator` 使用有界线程池；`ManifestOperator` 保持串行。
3. 主线程恢复顺序并汇总 metrics。
4. CLI 增加 `--workers/--executor` 覆盖参数。
5. 增加串行与并发输出一致性测试。

### P2：Checkpoint

1. 每批次原子写入 checkpoint part。
2. 保存配置摘要、Operator 版本和完成状态。
3. 支持 `--resume <run_id>`，验证中断恢复不重复计算。

### P3：Manifest 分片

1. 增加 shard、run-shards、merge 命令。
2. 支持多个独立 Pipeline 进程并行。
3. 合并时执行完整性、去重和 schema 校验。

### P4：按基准结果优化

1. 对特定 CPU 密集步骤试验进程池。
2. 根据音频时长做负载均衡。
3. 若单机仍不足，再接入 Ray、Dask、Celery 或批处理平台；在此之前不建议引入分布式依赖。

## 10. 测试与验收标准

先建立固定的 1 千、1 万、10 万条基准集，记录串行基线。验收至少包含：

- 相同输入和配置下，并发与串行最终 Manifest 内容一致，允许完成时间和日志顺序不同。
- 最终样本顺序确定，多次运行结果一致。
- 同名文件不会覆盖，cache JSON 和派生音频不存在半文件。
- 任意杀死进程后可以恢复，已完成样本通过 checkpoint 或 cache 跳过。
- 单条损坏音频只标记该样本失败，不使 worker pool 整体退出。
- 10 万条运行过程中 Future 数量受 `max_in_flight` 限制，内存不会随样本总数持续增长。
- 输出数满足：`成功 + 失败（未 select 前） = 输入数`。
- 在目标机器上，线程池版本整体吞吐相对串行至少提升 2 倍；若未达到，应先定位 CPU、
  磁盘或内存瓶颈，而不是继续盲目增加 workers。

建议基准指标：

```text
samples/s
audio_hours/hour
各步骤 p50/p95 单样本耗时
cache hit 比例
失败率
进程峰值内存
CPU 利用率
磁盘吞吐与队列长度
```

## 11. 针对当前项目的最终建议

对现有代码，最合适的近期方案不是立刻引入分布式框架，而是：

1. 先修复 cache 与派生音频的并发写安全。
2. 在 `_run_step()` 中为 `BaseOperator` 引入有界线程池，默认 4～8 workers。
3. 按步骤独立调节并发，重采样保守，probe/filter 较高。
4. 每 1000 条落一个 checkpoint。
5. 单机验证稳定后，再把 10 万～20 万条 Manifest 切成 8～32 个稳定 shard，同时运行
   2～4 个 shard pipeline。

该路径保留现有 Manifest、Operator 和 cache 设计，改造范围可控，也为后续多机执行保留
清晰的扩展边界。
