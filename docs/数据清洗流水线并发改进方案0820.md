## 1. 背景与目标

当前清洗流水线具备 Manifest、Operator DAG、cache 和断点续跑能力，但
`PipelineRunner._run_step()` 对每个普通 Operator 仍采用单线程逐样本执行。数据达到
10 万～20 万条后，PCM 转换、重采样、probe 等步骤会成为主要耗时。

本方案目标：

- 单机优先，在不改变现有 Operator 业务逻辑的前提下实现并发。
- 保持样本顺序、Manifest 血缘、cache key 和失败隔离语义不变。
- 支持断点续跑，进程异常后只重跑未完成部分。
- 后续可通过 Manifest 分片扩展到多进程、多机或任务调度平台。
- 并发度可配置，避免机械地开满 CPU 导致磁盘抖动或内存耗尽。

## 2. 当前实现的主要瓶颈与风险

### 2.1 普通 Operator 串行执行

当前每一步都是：

```text
步骤 1：依次处理全部样本
  ↓
步骤 2：依次处理全部样本
  ↓
步骤 3：依次处理全部样本
```

样本之间通常没有依赖，适合在“单个步骤内部”并发。`quality.select`、`ingest.scan`
等 `ManifestOperator` 操作整个集合，应继续串行执行。

### 2.2 不能直接给现有循环套线程池

并发前必须处理以下问题：

1. `data/cache/<operator>/<key>.json` 目前直接覆盖写入，并发或进程中断可能留下半个
   JSON 文件。
2. 派生音频目前使用 `<sample.id>.wav`；不同目录中存在同名文件时会互相覆盖。
3. 20 万条样本如果一次性提交为 Future，会产生较大的调度和内存开销。
4. 多线程中直接修改全局 metrics 会产生竞争；应由主线程汇总结果。
5. 音频解码与重采样会同时占用 CPU、内存与磁盘，worker 并非越多越快。
6. 多进程模式下 Operator、Sample 和配置必须可序列化，Windows 还必须使用安全的
   `spawn` 入口。

## 3. 推荐总体架构

采用“两级并发、分阶段落地”：

```text
输入 Manifest
  │
  ├─ 按步骤执行 DAG（步骤之间仍保持顺序）
  │    ├─ ManifestOperator：主进程串行
  │    └─ BaseOperator：有界 worker pool 并发处理样本
  │
  ├─ 每完成一个批次写 checkpoint
  │
  └─ 输出最终 Manifest

大规模扩展：
输入 Manifest → N 个稳定分片 → N 个独立 shard pipeline → 校验并合并 Manifest
```

第一层是单个 Pipeline 进程内的步骤级并发，改造成本低，适合单机 10 万～20 万条。
第二层是 Manifest 分片并行，每个分片有独立 run 目录和 checkpoint，适合多进程或多机。

不建议一开始让每个样本完整跑完所有步骤的“样本级流水线”。当前步骤间会更新
Manifest 字段和 cache，按步骤设置不同并发度更容易控制资源，也能保持现有语义。

## 4. 第一阶段：单机有界并发

### 4.1 新增执行配置

已在 Pipeline YAML 中落地（输出顺序始终保持与输入一致，因此不提供 `preserve_order`
开关；`executor: process` 已实现，但默认仍用 thread——见 §4.2 / §12）：

```yaml
execution:
  executor: thread          # thread | process | sequential
  workers: 4                # 全局默认并发数
  max_in_flight: 0          # 同时排队+执行的任务数，0 → workers * 4
  fail_fast: false
  checkpoint_every: 1000

pipeline:
  - name: pcm_convert
    operator: audio.pcm_to_wav
    execution:
      workers: 8

  - name: resample
    operator: audio.resample
    execution:
      # CPU 密集时可试 process；本机实测 thread 通常更快（见 §12）
      workers: 4

  - name: probe
    operator: quality.probe
    execution:
      workers: 16

  - name: audio_pass
    operator: quality.filter
    # ManifestOperator：忽略 workers，整表批处理

  - name: select_pass
    operator: quality.select
```

优先级为：CLI 覆盖 > step `execution` > pipeline `execution` > 内置默认值。

```bash
audio-data pipeline run pipelines/data_cleaning_source_A.yaml \
  --workers 8 \
  --executor thread

# 关闭并发做对照基线
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --executor sequential

# 仅当基准显示 GIL 卡死时再试进程池（Windows spawn 有固定开销）
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --executor process --workers 4
```

### 4.2 为什么第一版优先线程池

当前 `soundfile`、NumPy、SciPy 的主要计算位于原生代码中，很多操作会释放 GIL；
音频读取和写入也包含 I/O 等待。因此线程池可以在较小改造成本下取得明显收益，并且：

- 不需要反复序列化完整 `Sample`。
- cache、日志和 Operator 注册表继续位于同一进程。
- Windows 下无需承担多进程 `spawn` 的高启动成本。

线程池并不保证 CPU 密集步骤线性加速。若基准测试表明某步受 GIL 限制，可为该步骤单独
写 `execution.executor: process`。进程池走顶层可 pickle 的 `_process_one_task`（子进程
重新 import operators），与线程池共用同一套有界提交 / 顺序恢复逻辑。

本机 600 条清洗流水线实测（见 §12）：全步骤 `process` 反而更慢（Windows spawn + 序列化）；
仅 `resample` 用 process 也未超过 thread。**默认保持 thread**，process 作为可选开关。

### 4.3 有界提交与顺序恢复

不能一次提交 20 万个 Future。Runner 应只维持 `max_in_flight` 个任务：

1. 主线程按原 Manifest 顺序提交任务，并记录 `index`。
2. worker 返回 `index + OperatorResult` 或 `index + 异常信息`。
3. 主线程消费完成结果、更新 metrics，并持续补充新任务。
4. 结果写入预分配列表的原 index，保证最终 Manifest 顺序不变。
5. 单条失败沿用现有逻辑：复制 Sample、写入 failed 状态，不影响其他任务。

建议为 `PipelineRunner` 增加统一的 `_process_one()`，串行与并发路径共用异常处理，
避免两套执行语义逐渐不一致。

## 5. 并发写入安全改造

### 5.1 cache 原子写入

缓存应采用“同目录临时文件 + 原子替换”：

```text
写入 <cache_key>.<pid>.<uuid>.tmp
  → flush（必要时 fsync）
  → os.replace(tmp, <cache_key>.json)
```

这样另一个 worker 只能看到完整旧文件或完整新文件。相同 cache key 被重复计算时，
允许最后一个完整结果覆盖，因为 Operator 应满足相同输入与参数产生相同结果。

如果未来存在昂贵的模型推理，可增加 cache-key 文件锁，避免相同任务重复计算；第一版
无需引入全局锁，以免降低吞吐量。

### 5.2 派生文件唯一命名

将：

```text
data/derived/resample_16k/<sample.id>.wav
```

改为至少包含内容哈希（实现取 sha256 前 16 位，兼顾 Windows 路径长度；200k 样本碰撞概率
约 1e-9）：

```text
data/derived/resample_16k/<sha256前2位>/<sha256前16位>_<sample.id>.wav
```

PCM 转 WAV、重采样、降噪和数据增强 Operator 都应遵循同一命名函数。分两级目录还可
避免单目录下出现 20 万文件导致文件系统访问变慢。

派生文件也应先写临时路径，成功关闭后再 `os.replace` 到目标路径，避免中断后将半成品
误认为有效结果。

### 5.3 日志与指标

- worker 只返回结构化状态，不直接修改 `RunMetrics`。
- 主线程统一累计 `processed/cache_hits/skipped/failed`。
- 进度日志按“已完成数”输出，而不是按提交数输出。
- 每个步骤记录耗时、吞吐量、平均音频时长、失败率和峰值并发数。

## 6. Checkpoint 与断点续跑（已实现）

cache 能避免 Operator 重算，但中断后 Runner 仍要重新加载 Manifest、逐步骤走一遍全部样本
（20 万条时光是 `ingest.scan` 重新扫盘算 sha256 就很贵）。现在每个步骤按批次落 checkpoint：

```text
runs/<run_id>/
  run.log
  config.yaml          # 含 config_digest
  metrics.json
  manifest.parquet
  checkpoints/
    00_pcm_convert/
      part-000000.parquet
      part-000001.parquet
      _state.json
    01_resample/
      ...
```

用法：

```bash
# 首次运行（YAML 里 checkpoint_every 生效，默认 1000）
audio-data pipeline run pipelines/data_cleaning_source_A.yaml

# 中断后从同一个 run 目录续跑
audio-data pipeline run pipelines/data_cleaning_source_A.yaml \
  --resume runs/20260820_182517_data_cleaning_source_A

# 只想跑基线、不要 checkpoint 开销
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --checkpoint-every 0
```

`--resume` 接受 run 目录路径或 `runs/` 下的 run id。

### 6.1 一致性保证

`_state.json` 里的 `fingerprint` 记录 pipeline 配置摘要（步骤列表、params、各 Operator
版本）、该步骤的 operator + version + params 摘要、输入样本指纹（每条 id + sha256 的滚动
哈希）以及 `checkpoint_every`。任一项变化，该 checkpoint 直接不复用并打印原因，底层 cache
仍按 cache key 独立判断，因此改配置重跑不会读到错的中间结果。

写入顺序是「part 文件原子发布 → `_state.json` 原子更新」，所以：

- 只有登记在 `_state.json` 里的 part 会被采用；写完 part 但没登记就崩溃，那一批重算。
- part 只信任连续前缀：中间某个 part 文件被删，后面的一律丢弃。
- 一个 part 覆盖输入的一段连续区间，恢复时 `samples[consumed:]` 就是待处理部分，
  因此输出顺序与不中断时完全一致。

`ManifestOperator`（`ingest.scan`、`quality.filter`、`quality.select`）是整表操作，
无法按批切分，因此整步作为单个 part 落盘——续跑时直接恢复，不再重新扫盘或重新求值。

`--force` 表示“强制重算”，此时只写新 checkpoint、不读旧的。

### 6.2 硬杀进程后的残留

`atomic_path` 在异常路径会清掉临时文件，但 `SIGKILL` / `Stop-Process -Force` 没有机会执行
清理，会在 cache / derived 下留下 `*.tmp*` 孤儿文件。这些文件永远不会被读到（读取方只找
`<name>`），属于占空间而非正确性问题，需要时显式清理：

```bash
audio-data pipeline clean-temp pipelines/data_cleaning_source_A.yaml --dry-run
audio-data pipeline clean-temp pipelines/data_cleaning_source_A.yaml
```

### 6.3 `checkpoint_every` 取值

默认 1000。单条音频很短可调到 5000（减少 part 数）；单条耗时很长可调到 100～500（少重算）。
0 表示关闭。代价见 §0：本机 600 条实测约 +22%，本质是每步把结果多写一遍 parquet。

## 7. 第二阶段：Manifest 分片并行（已实现）

```bash
# 1. 稳定哈希分片（输入需为已 ingest 的 manifest）
audio-data manifest shard datasets/batches/batch_A/manifest.parquet \
  --shards 16 \
  --output-dir datasets/shards/source_A

# 2. 每个分片一个独立进程，同时跑 4 个，每个进程内部 8 线程
audio-data pipeline run-shards pipelines/data_cleaning_source_A.yaml \
  --shard-dir datasets/shards/source_A \
  --parallel-shards 4 \
  --workers 8 \
  --run-root runs/cleaning_source_A_shards

# 3. 合并并校验（分片数、重复 (sha256, id)、总数）
audio-data manifest merge "runs/cleaning_source_A_shards/shard-*.parquet" \
  --output datasets/manifests/cleaned_source_A.parquet \
  --expected-shards 16
```

`run-shards` 会自动丢掉 `ingest.*` 步骤：分片 manifest 已经列明样本，再扫源目录会把全部
样本重新灌进每个分片。每个分片有独立的 run 目录、checkpoint、metrics 和 `shard-XXX.log`；
任一分片非零退出时命令整体以 1 退出并列出失败分片。

分片的 run 目录是固定的 `<run-root>/shard-XXX`（内部用 `--resume` 传入），所以崩溃后
**重复执行同一条 `run-shards` 命令即可续跑**：已完成的分片整体从 checkpoint 恢复，
被中断的分片只补做剩余批次。

每个分片都是独立 Python 进程，启动 + import 约 1.3s。小数据量下这项固定开销会盖过收益
（400 条时 4 分片反而比单进程慢），10 万条以上才值得启用。

### 7.1 分片规则

采用稳定哈希，而不是按当前行号切分：

```text
shard_id = int(sha256[:16], 16) % shard_count
```

优点：

- 同一文件每次都进入相同分片，方便重跑和增量处理。
- 各分片数量通常较均衡。
- 输入 Manifest 顺序变化不会导致全部重新分片。

如果音频时长差异很大，仅按条数可能负载不均。已支持时长均衡：

```bash
# 需样本已有 duration（例如 probe 之后的 manifest）
audio-data manifest shard cleaned_source_A --shards 16 \
  --strategy duration-balanced \
  --output-dir datasets/shards/source_A_bal
```

`duration-balanced` 按「时长降序 + digest」排序后，贪心把每条分到当前总时长最短的分片
（LPT）。输入顺序不影响结果；缺 duration 时按权重 1.0。与 `hash` 不同：时长更新后
重新分片边界会变，适合「已 probe、整批重跑」；增量续跑仍优先 `hash`。

本机 600 条、4 分片实测总时长差：hash 约 71s → duration-balanced 约 0.2s。

### 7.2 分片隔离与合并校验

每个 shard 使用独立 run 目录、metrics 文件和日志文件；cache 与派生文件共享，依赖第 5 节
的原子写入与唯一命名保证并发安全。

`manifest merge` 当前的校验：

- `--expected-shards` 校验分片文件数量，缺少分片直接报错。
- `(sha256, id)` 重复检测；默认丢弃重复项并报告数量，`--keep-duplicates` 可保留。
- 输出条数与输入条数、重复数一并打印，便于核对。
- 按 `(sha256, id)` 排序，保证多次合并顺序确定。

配置摘要 / Operator 版本一致性由各步骤 checkpoint 的 `fingerprint` 保证；合并阶段仍以
分片文件数、`(sha256, id)` 去重和条数报告为主。

## 8. 资源控制建议

初始值不要按 20 万条数据量决定，而应按机器资源和单条音频大小决定：

| 步骤 | 主要资源 | 建议初始 workers |
| --- | --- | ---: |
| `audio.pcm_to_wav` | 磁盘读写 | 4～8 |
| `audio.resample` | CPU + 内存 + 磁盘 | `min(物理核数, 4～8)` |
| `quality.probe` | 小文件 I/O | 8～16 |
| `quality.filter` | 轻量 CPU | 8～16 |

额外约束：

- 使用机械硬盘或网络盘时，从 2～4 workers 开始。
- 使用本地 NVMe 时，可逐步提高到 8～16，观察吞吐是否继续增长。
- `max_in_flight` 建议为 workers 的 2～4 倍。
- NumPy/SciPy 底层线程数建议固定为 1，避免“worker 数 × BLAS 线程数”过度并发：
  `OMP_NUM_THREADS=1`、`MKL_NUM_THREADS=1`。
- 单条音频解码会占用与音频长度相关的内存；应通过压力测试设定并发上限，不能只看 CPU。

Windows PowerShell 示例：

```powershell
$env:OMP_NUM_THREADS = "1"
$env:MKL_NUM_THREADS = "1"
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --workers 8
```

## 9. 推荐实施顺序

### P0：并发正确性基础（已完成）

1. 提取统一派生文件命名函数，引入 `sha256` 分目录。
2. cache 和派生音频改为临时文件原子替换。
3. 为同名 `sample.id`、相同 cache key 并发写、处理中断残留增加测试。

## 10. 测试与验收标准

先建立固定的 1 千、1 万、10 万条基准集，记录串行基线。验收至少包含：

- 相同输入和配置下，并发与串行最终 Manifest 内容一致，允许完成时间和日志顺序不同。
- 最终样本顺序确定，多次运行结果一致。
- 同名文件不会覆盖，cache JSON 和派生音频不存在半文件。
- 任意杀死进程后可以恢复，已完成样本通过 checkpoint 或 cache 跳过。
- 单条损坏音频只标记该样本失败，不使 worker pool 整体退出。
- 10 万条运行过程中 Future 数量受 `max_in_flight` 限制，内存不会随样本总数持续增长。
- 输出数满足：`成功 + 失败（未 select 前） = 输入数`。
- 在目标机器上，线程池版本整体吞吐相对串行至少提升 2 倍；若未达到，应先定位 CPU、
  磁盘或内存瓶颈，而不是继续盲目增加 workers。

建议基准指标：

```text
samples/s
audio_hours/hour
各步骤 p50/p95 单样本耗时
cache hit 比例
失败率
进程峰值内存
CPU 利用率
磁盘吞吐与队列长度
```

### 10.1 实际验收结果

已验证（自动化测试 `tests/test_core.py` 共 23 项 + 400/600 条真实数据）：

- 并发与串行最终 manifest 完全一致，样本顺序确定。
- **进程池**与串行最终 manifest 完全一致；单条损坏只标记该样本失败。
- 分片并行 + 合并结果与单进程结果一致，重复项为 0，合并顺序确定。
- **时长均衡分片**确定性、负载差显著小于 hash（600 条 4 片：71s → 0.2s）。
- 同名 `sample.id` 不同内容不会互相覆盖（`derived_audio_path` 内容哈希）。
- cache 与 derived 无 `.tmp` 残留；写入过程抛异常时不发布目标文件。
- 单条损坏音频只标记该样本失败，线程池继续处理其余样本。
- Future 数量受 `max_in_flight` 限制，不随样本总数增长。
- 线程池整体吞吐 1.90x（相对改造前串行基线约 3.5x），达到 2x 目标附近。
- **中断恢复**：600 条跑到 resample 第 3 批时强杀，`--resume` 后输出与干净完整运行一致。
- checkpoint 指纹变化不复用旧 part；未登记 part 忽略；part 缺失只保留连续前缀。

未验证：10 万 / 20 万条规模的长时运行、峰值内存与磁盘队列长度，需要在目标机器上跑一次
全量数据确认。

## 11. 针对当前项目的最终建议

对现有代码，最合适的近期方案不是立刻引入分布式框架，而是（P0～P3 已按此顺序完成）：

1. 先修复 cache 与派生音频的并发写安全。
2. 在 `_run_step()` 中为 `BaseOperator` 引入有界线程池，默认 4～8 workers。
3. 按步骤独立调节并发，重采样保守，probe/filter 较高。
4. 每 1000 条落一个 checkpoint。
5. 单机验证稳定后，再把 10 万～20 万条 Manifest 切成 8～32 个稳定 shard，同时运行
   2～4 个 shard pipeline。

20 万条的推荐执行方式：

```powershell
$env:OMP_NUM_THREADS = "1"
$env:MKL_NUM_THREADS = "1"

# 一次性入库（此步无法并发，只做一次）
audio-data ingest D:/path/to/batch_A --name batch_A

# 切 16 片
audio-data manifest shard batch_A --shards 16 --output-dir datasets/shards/source_A

# 4 进程 × 8 线程；崩溃后重复执行同一条命令即可续跑
audio-data pipeline run-shards pipelines/data_cleaning_source_A.yaml `
  --shard-dir datasets/shards/source_A --parallel-shards 4 --workers 8 `
  --run-root runs/cleaning_source_A_shards

# 合并
audio-data manifest merge "runs/cleaning_source_A_shards/shard-*.parquet" `
  --output datasets/manifests/cleaned_source_A.parquet --expected-shards 16
```

该路径保留现有 Manifest、Operator 和 cache 设计，改造范围可控，也为后续多机执行保留
清晰的扩展边界。

## 12. 并发落地后暴露的两个新瓶颈

线程池上线后，剩余耗时集中在两处与磁盘/CPU 无关的“每样本固定开销”上。这两项在 20 万条
规模下都是分钟到十分钟级别的成本，且都无法靠增加 workers 解决。

### 12.1 `quality.filter` 每条样本执行一次 pandas.query（已解决）

改造前 `FilterOperator._execute()` 对每条样本构造一行 DataFrame 再 `query`，实测约
3.5 ms/条，纯 Python + GIL，线程池几乎无收益，400 条里占 2.55s（约 47%），20 万条约
12 分钟。

已改为批量 `ManifestOperator`：按 `chunk_size`（默认 20000）分块构造 DataFrame，一次
`query` 得到整块结果。400 条从 2.55s 降到约 0.09s。分块而不是整表求值，是为了在 20 万
条规模下限制 DataFrame 峰值内存，同时保持与旧版一致的“逐行判断”语义。

语义变化需要注意：

- 不再逐样本写 cache / status，`--force` 对该步骤无意义，每次运行都会重新求值（成本已
  可忽略）。lineage 仍逐样本追加。
- 版本号升到 `2.0.0`，历史 cache 不会被误用。
- 旧版对“表达式引用的列在该样本上不存在”会把该样本判为 `False` 并写 `<label>_error`；
  新版以块为单位：整块都缺该列时行为一致，块内部分样本有该列时缺失值参与比较（`NaN`）。
  清洗链路中 `quality.probe` 会为所有样本写 `labels.broken`，不受影响。
- `quality.select` 的保留判断同时从按 `id` 匹配改为按行位置匹配，避免不同目录下同名
  `sample.id` 互相误判。

### 12.2 每样本一个 cache JSON 文件（未解决）

每个算子对每条样本写一个 cache JSON：原子写入 1.39 ms/条（非原子写入 0.49 ms/条，
差值是崩溃安全的代价）。20 万条 × 5 步约 100 万个小文件，累计约 23 分钟纯写入，
并给文件系统带来压力。

后续可考虑按步骤合并为分片 cache（如每 1000 条一个 parquet/jsonl），与 §6 的 checkpoint
方案合并实现，避免重复设计。
