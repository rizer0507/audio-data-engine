# 0908 三万条分拣结果复盘

分析日期：2026-09-10。对象：本地 `0908-30000` 最新分拣产物和当前工作区代码。本文记录观测事实与原因，不替代现行规则；重构目标见 [020-分拣流水线重构](../04-改进需求/进行中/020-分拣流水线重构.md)（已深度规格化；Phase 1 导出交集已落地，业务门禁未过）。

## 1. 结论

**这次分拣没有实现“减少人工、产出可用训练数据”的业务目标。26,071 条进入普通人工队列，占输入的 86.90%；自动伪标签候选为 0。问题不能归结为音频本身太难。**

主要原因有三层：

1. **明确的导出缺陷**：指定 P0 和 `manual_review` 时，队列条件绕过了优先级条件，P0 包混入 16,156 条 P1。真正的 P0 是 9,915 条。
2. **设计目标偏离**：把质量未校准、模型分歧、内容敏感、推理不稳定统一转成逐条人工盲标；机器处理和暂存出口不足，校准与训练集准入又没有准备好。风险识别被直接当成了人工任务生成器。
3. **发布条件根本未满足**：全部 30,000 条质量状态 unknown，全部被 `governance_hold` 隔离。即使完成这批人工转写，也不会自动解决分组元数据和质量校准缺口。

我此前设计与交付的不足，是把保守门禁落了地，却没有同时把机器修复、预算调度、质量校准和业务产出验收组成完整闭环。工程实现完成不能代表这套流水线已达到可用的人工节省率。

## 3. 三万条最终去了哪里

按互斥的 `review_queue` 统计：

- 普通人工 `manual_review`：26,071，86.90%。
- 留言隔离 `voicemail_isolation`：1,881，6.27%。
- 语速异常排除 `exclude`：1,381，4.60%。
- 推理不完整重试 `retry`：667，2.22%。

四个队列之和精确等于 30,000。留言隔离的 `decision` 同样是 `manual_review`，因此按 decision 统计的人工判定为 **27,952 条（93.17%）**。不能把普通人工包之外的 3,929 条说成“自动标好了”；其中没有自动产出的伪标签。

普通人工队列按主类别分解：

- `critical_content_risk`：6,399，全部 P0。
- `semantic_risk`：2,768，全部 P0。
- `speech_presence_disagreement`：6,890，其中 P0 748、P1 6,142。
- `audio_quality_risk`：4,971，全部 P1。
- `all_empty_unverified`：4,285，全部 P1。
- `family_unstable`：479，全部 P1。
- `qwen_correction_candidate`：279，全部 P1。

前 3 类构成全部 P0：6,399 + 2,768 + 748 = 9,915。风险标签会重叠，不能把标签命中数再次相加当作样本数。

## 4. 根因与证据

### 4.1 P0 筛选确实失效，不是文件名理解错误

两个完整包的 `.meta.json` 均写着 `priorities: [P0]`、`queues: [manual_review]`，但实际包含 16,156 条 P1。

根因位于 [queue.py](../../src/audio_engine/core/annotation_v3/queue.py) 的 `select_review_batch`：优先级不匹配时，只要 queue 在 wanted_queues 内就不跳过。该例外注释原本意在支持没有 priority 的 `pseudo_audit`，实现却允许所有匹配队列的 P1/P2 绕过优先级过滤。

调用当时生产函数，以本批 30,000 条作为输入，设置 `priorities=['P0']`、`queues=['manual_review']`，复现输出 P0 9,915 + P1 16,156。**这会扩大单次交付任务，但不是原始 26,071 条进入 manual_review 的原因；两者必须分别修复。**

> **修复进度（020 Phase 1，2026-09-10）**：已改为 priorities∩queues 真交集；无 priority 队列仅在全优先级集或显式 `include_unprioritized` 时纳入。导出增加行集合与声明一致性校验及 `sample_set_digest`。历史错误包仍只读保留；重导出须新 revision。分类规则导致的 26,071 条人工不在本修复范围内。

`only` 文件已按内容分开，但同目录未发现各自的 meta 文件。拆表不等于重新生成有效审核包；需要原生重导出并验证不可变身份字段与导入契约。

### 4.2 未校准质量被变成了逐条标注任务

30,000 条全部 `dnsmos_status=success`，同时全部 `noise_band=unknown`、`noise_risk=null`。这是“有分数、无已校准判定”，不是 30,000 条评分失败，也不是 30,000 条实际噪声很大。

[DNSMOS 配置](../../configs/quality/dnsmos_p835.yaml) 为 `calibrated: false`；[dnsmos_p835.py](../../src/audio_engine/core/quality/dnsmos_p835.py) 明确在未校准时返回 unknown/null。[classifier.py](../../src/audio_engine/core/selection_v3/classifier.py) 将其归为 `quality_unknown`，在完整共识分支前以 `audio_quality_risk` 返回人工。

直接以该主因进人工的 4,971 条中，**2,633 条六路比较文本完全一致且非空**。例如 `fenshen-276cc46a-bf3387be`，6.7 秒，六路均为“喂啊你好谁啊”，却无候选文本、进入 P1。

使用当前生产分类器复算这 4,971 条，基线全部复现 `audio_quality_risk`。仅在内存中假设其质量全部合格，其他数据不变，结果为：

- `pseudo_high`：2,634。
- `pseudo_medium`：90，现行规则仍需人工。
- `hardcase`：2,247，现行规则仍需人工。

这是用于归因的**乐观反事实上限**，不是真实质量结论或可直接发布量。2,634 与完全一致的 2,633 不同，是因为高置信分支允许长句相似度达到 0.98。只修质量门禁也不可能消除全部人工任务；还需要抽审通过与治理解锁。不能简单把 `calibrated` 改为 true 伪造校准完成。

### 4.3 把“内容本身有肯否词”误当成“模型之间有语义分歧”

[semantic_risk.py](../../src/audio_engine/core/selection_v3/semantic_risk.py) 的 `polarity_of_text` 用词表子串匹配；同一文本出现肯定和否定材料可判 `mixed`。`conflict_tags_for_texts` 只要看见 mixed 就添加 `critical_token_conflict`，不要求两个文本实际不同。同族稳定性又调用这套函数，造成相同文本也被标为 `unstable_semantic`。

本批有 **88 条六路比较文本完全相同，仍被归为 P0 critical_content_risk**。例如：

- `fenshen-50c90055-1da56874`：“啊是最近没有好的”。
- `fenshen-e3a34094-d55fcb68`：“啊不是不是别人给我的手机号”。
- `fenshen-17196c56-f4f24fa1`：“没有吧你是你属于是平安银行系统的吗”。

这证明了“模型间分歧”的归因不准确，不代表这些音频的真实转写已经确认正确。

> **修复进度（020 Phase 3，2026-09-10）**：相同比较文本不再产生模型间冲突或同族语义不稳；可记 `content_complexity`（P2 抽审）。对历史 classified 只读回放：上述 88 条 live 重分类全部变为 `content_complexity`，无残留 P0 模型冲突。生产默认分拣队列未因本项自动重写落盘产物——需重新跑 classify 才写入新 type。

此外，词表将“嗯”“啊”“好”“有”“是”等高频词与真正关键实体放入同一冲突通道。如“你说”对“嗯你说”、“没有了谢谢”对“没有了谢谢啊”均触发 P0。语气词差异可能需要保留，但其业务风险与“需要/不需要”的含义反转不同，不应无差别采用最高成本审核。

### 4.4 首个风险直接返回，阻断候选和共识信息

当前分类顺序先处理语义、关键内容、全空、空/非空混合、留言、Qwen 纠错、同族不稳、质量风险，最后才进入完整共识。任何一家族不稳定即可挡住后续分支；短句使用完全一致而非 0.98，相比长句更严。

19,416 条被标短句，其中 17,720 条时长大于 2 秒：规则还允许“任一路有效文本≤6字”触发。这是配置定义，不是计数错误，但短文本对整条样本约束很广，需按真实错误率校准。

普通人工队列的 classified 标签中，仅 279 条 Qwen 纠错主类别保留非空 candidate_text。其余大多数不是已经确认无候选，而是提前返回没有生成候选。blind 导出还会有意清空候选字段。这套流程适合独立金标采集，却不能作为所有训练候选默认的低成本加工方式。

4,285 条全空、6,890 条有声/无声分歧需要独立音频证据才能判断，不能仅靠文本多数票自动认定静音。本次未听音，不能给出它们的真实误识别率。重构应提供专门的语音存在性确认、机器重试和按用途抽样，而不是一律要求整条重转写。

### 4.5 全部样本治理隔离，人工转写不能修复

30,000 条全部 `dataset_role=governance_hold`，均有 `missing_group_metadata`。配置要求可靠分组及 source index，缺失时隔离。普通人工包中的 `reservation_role` 也全部为 governance_hold。

这不是本次人工队列数量的直接分类原因，却是业务不可交付的独立阻断。人工标注解决 transcript，不会自动补齐通话/说话人/源索引及防泄漏证据。应先补来源关联并重新冻结分配；若仍不满足，则只允许明确的诊断用途，不能把全量隔离池包装成生产标注任务。

### 4.6 工作量比“26,000 条”更高，且存在重复劳动

完整人工包中 20,342 条要求双审，5,729 条单审。若逐条执行，至少是 **26,071 次初审 + 20,342 次复审 = 46,413 次审核作业**，未包含冲突仲裁、抽检和返工。

26,071 条对应 24,417 个原音频 SHA-256，也对应 24,417 个 leakage_group_id，存在 1,654 个超出唯一音频数的记录。可以研究同音频、同标注范围复用结果；不能按相同文本盲目去重，也不能省掉独立双审。

### 4.7 “排除”也不是分拣成功

1,381 条因任一路不可能语速而整条排除；触发路次主要来自 GLM（第一跑 1,304、第二跑 1,250，存在重叠）。其中 36 条 Qwen 与 SenseVoice 四路比较文本相同且非空。

这不证明 36 条一定可用，但说明单模型幻觉可能误伤整个样本。应先隔离失效路次、保留原始证据、重试并重算剩余有效家族，不应把模型输出异常直接等同音频无效。

> **修复进度（020 Phase 3，2026-09-10）**：`speech_rate.disposition=route_quarantine` 或 `refactor_020_mode=on|shadow` 时改为路次隔离+重算；剩余独立家族不足 → `route_quarantine`/`retry`。默认仍为 `exclude`（018 兼容）。影子流水线：`pipelines/classify_dataset_v3_shadow_020.yaml`。

## 5. 应当怎么处理当前批次

1. 停止把现有 26,071 条包解释为“现在必须全部完成的 P0 任务”；修正优先级与队列交集语义，重导出带独立 meta 的审核包。
2. 先完成批次可用性诊断：补分组与源索引，制定独立质量校准计划。治理和评分问题由流水线处理，不让标注员重复承担。
3. 分开交付少量校准/金标盲审任务、训练候选校对任务、语音存在性确认任务。批次待审池与本轮人工预算分别记录。
4. 将“文本完全一致却被判冲突”、质量 unknown、异常路次和相同音频重复记录列为回放重点，先影子运行再改变生产规则。
5. 以抽审错误率、关键语义错误、可发布量和人工时长共同验收。不得只靠降低阈值、批量排除、改队列名或缩小导出条数宣称节省人工。

不能根据当前文件可信地承诺“重构后只需标 N 条”。本次最多证明现有设计与导出存在系统性问题；真正的必要人工量需要独立校准和听音验证。
