# 047｜指定 batch 整批保音高加速增强流水线

日期：2026-10-16。状态：**代码已交付**（工程验收：`pytest tests/test_augment_tempo.py`；真实语音听验与目标服务器吞吐待验）。

项目：`audio-data-engine`。交付用途：交给 Cursor 在当前公用引擎库中实现。

## 1. 我想做什么

新增一条独立的数据增强流水线：指定一个 batch，对该 batch 输入快照中的全部音频样本进行增强，生成一批新的增强音频及配套 Parquet，供后续训练或其他流水线使用。

**首版只实现加速，倍率通过参数指定，默认 `1.2`。** 用户已确认：**加快语速、保持音高**，不能使用会同时提高音高的简单变速重采样替代。

例如，一段约 6 秒的音频按 1.2 倍增强后，时长约为 5 秒，语速更快，音高基本保持。原始音频与原 batch 数据不覆盖、不修改。

要求是一条标准 `audio-data pipeline run` 命令完成整批处理，支持有界并发、自动分片、缓存、进度和断点续跑。首版不实现加噪、音量变化、混响、随机倍率或多种增强组合。

## 2. 业务范围与默认决策

1. 每条输入样本生成一条加速后的派生样本；同一运行整批使用同一个倍率。
2. “整批”指**本次绑定的 batch 输入快照的所有行**，不随机抽样，不按标签、类别、是否有金标等条件过滤。
3. 若输入是 VAD 片段，增强单元就是片段；不能退回父录音重新切分，也不能把父录音和片段混在一起重复增强。
4. 增强产物独立保存，默认输出只包含新生成的增强样本；原样本继续保留在上游。首版不要求额外生成“原始 + 增强”的合并训练集。
5. 不自动重跑 ASR、VAD、DNSMOS、语义判断、自由标签或人工标注；需要重算时，由下游显式运行。
6. 未标注、明确不做训练等样本仍按整批规则增强，但保留其使用限制，**不因增强而自动变成可训练正样本**。
7. 默认禁止把已经增强过的 batch 当作普通输入再次增强，防止重复运行时变成 `1.2 × 1.2`。首版不要求支持级联增强。

## 4. batch 定位与输入契约

### 4.1 指定 batch

沿用现有 CLI 的 `--source-name <batch>`，手册中明确 source-name 在本流水线表示批次标识，不新增另一套含义相同的必填 batch 参数。

首版默认输入规则：

```text
--source-name batch_A
→ datasets/stage1/segments/segments_batch_A.parquet
```

这是当前生产链的片段快照默认值，不要求 batch 必须已经完成 ASR、打标或入仓。

支持通过现有 `--input-manifest` 显式覆盖为该 batch 的清洗、标注、准备证据或冻结仓库 Manifest。例如已入仓数据可明确指定 `datasets/stage1/warehouses/batch_A/manifest.parquet`。

要求：

- 固定绑定一个输入快照，记录解析后的绝对路径、内容摘要及行数；恢复时不能换成目录里“最新的一份”。
- 默认快照不存在时清晰报错并说明如何显式指定，不擅自改用父源、旧分类结果或其他 batch。
- 不扫描目录后将同 batch 的不同阶段 Manifest 统统合并；不同阶段可能是同一数据的重复视图。
- 显式路径与 batch 元数据不一致时预检报错。旧 Manifest 没有 batch 字段时，允许操作者通过 `--source-name` 显式绑定并记录绑定来源。
- 输入快照含多个 batch 时拒绝整份处理，不默默只取其中一部分。
- 同一快照重复 id、非法结构、空 batch 等全局问题在预检报错。空快照应明确报告“无可增强数据”，不标为成功生成增强集。

### 4.2 选择实际音频

默认 `input_audio_key=resampled_16k`，显式参数可改为 `raw` 或其他 key。

- 使用 `sample.audio[input_audio_key]` 指向的当前样本音频；仅在明确配置 `raw` 时允许既有 `source_path` 回退。
- 所选 key 缺失时记为该行失败，不能悄悄改用其他 key 或父音频。
- 首版默认处理带格式头且可解码的音频；裸 PCM 需显式提供采样率、声道和位宽，或先使用既有规范化流水线转成 WAV，不能凭文件大小猜格式。
- 采样率、声道数、帧数及输入时长以实际解码/音频头为准；与旧元数据不一致时记录诊断。
- 不要求输入包含识别文本、金标或声学评分。

## 5. 加速参数与保音高算法

### 5.1 参数语义

对外参数统一命名为 `speed_factor`，首版新增 `pipeline run --speed-factor <数值>`，并支持 YAML 配置。该参数适用于本增强算子，不应被静默注入无关流水线。

- 默认值：`1.2`。
- 意义：播放/语速倍率，`输出时长 ≈ 输入时长 / speed_factor`。
- 首版只接受有限、有效且严格大于 1 的数值；0、负数、1、NaN、Infinity、布尔值和非法字符串在预检拒绝。
- `1.2`、`1.20` 等等价输入归一为同一参数身份；不同有效数值不能因为仅保留两位小数而共用路径或缓存。
- 不把倍率写死在音频后处理或文件名中；以冻结的生效参数为准。
- CLI 显式值优先于 YAML，YAML 缺省时使用 1.2；CLI 参数缺省不能意外覆盖 YAML 已配置值。
- CLI 的倍率必须传到所有子分片，并参与子流水线参数、检查点、缓存和输出命名。

不额外限制为固定的几个倍率，也不在首版新增随机倍率、倍率列表或减速模式。若极端倍率导致某条输入无法生成有效音频，按该行失败处理并说明原因。

### 5.2 算法要求

使用真正的保音高时间伸缩算法。首版建议采用 **FFmpeg `atempo`**，记录实际 FFmpeg 版本和滤镜参数；可以采用经过等价验证的其他后端，但不能静默切换为改变音高的重采样。

FFmpeg 官方将 `atempo` 定义为音频 tempo 调整滤镜，并指出超过 2 的单个倍率可能跳过采样，建议串联滤镜处理较大倍率。[官方文档](https://ffmpeg.org/ffmpeg-filters.html#atempo)

因此，若采用 FFmpeg：

- 用参数数组启动进程，不拼接可执行的 shell 命令；路径含空格、中文和特殊字符时仍正确。
- 大于 2 的倍率分解为多个不超过 2 的 atempo 阶段，乘积等于指定倍率，并记录实际滤镜链。
- 不通过改采样率标签、`asetrate` 或 `signal.resample` 冒充保音高加速。
- 子进程数量和单进程线程数均受并发预算约束；配置超时，异常中止时回收子进程。
- 预检后端存在、版本和所需滤镜可用；缺依赖时在批量处理前给出明确安装/配置说明。

### 5.3 音频输出

- 默认输出 WAV、PCM_16，采样率与所选输入一致，不额外升降采样。
- 默认保持输入声道数和声道对应关系，不静默取平均、取通道 0 或混音。生产输入通常已是单声道，此处不再重复规范化。
- 同一输入采用同一滤镜参数处理所有声道，避免声道不同步。
- duration、sample_rate、channels、帧数和内容摘要必须根据生成文件重新确认，不能只用理论公式填写。
- 对正常长度音频验证时长接近 `T/factor`；接受算法端点误差，不能为了强行凑帧数截掉正文或补入伪造语音。
- 零字节、解码失败、无帧数据、输出为空、写入失败或输出不可解码均记为失败；静音音频只要合法就正常增强，不当作坏样本过滤。
- 不额外裁剪静音、不再跑 VAD、不重复应用最短 1 秒等上游过滤规则。加速后不足上游最短时长并不意味着应在此丢弃。

## 6. 派生身份、血缘与标签

### 6.1 新样本身份

每个增强结果必须有独立、稳定且可复现的增强 id。建议由以下内容生成摘要：

```text
源 batch + 源 sample_id + 所选输入音频内容摘要
+ 增强类型 tempo + 归一化 speed_factor + 算法/后端版本及输出格式
```

id 可带可读的 `tempo` 前缀/后缀，但摘要不得只依赖文件 basename 或两位小数倍率。相同输入与处理指纹重复运行得到相同派生身份，不额外堆出重复样本；不同源片段、不同倍率或不同有效算法版本不会碰撞。

成功样本要求：

- `id` 为增强 id，`source_path` 为增强文件路径。
- `sha256` 指向当前增强音频的内容摘要，不能直接沿用原音频 SHA。
- 当前 `audio.raw` 和 `audio.aug_speed` 指向增强音频；只有实际采样率为 16 kHz 时才提供指向该文件的 `audio.resampled_16k` 别名。
- 元数据描述增强音频，原始音频路径和摘要通过明确的父级字段保留。
- `labels.augmentation` 至少记录类型、factor、保音高标志、源 batch、源 id、源 Manifest 摘要、输入 key/路径/摘要、输出摘要、输入输出时长、算法版本与处理指纹。
- 派生 batch 使用独立标识，例如 `<source_batch>__tempo_<factor_tag>_<recipe_digest>`；另存 `source_batch`。不能覆盖或替换原 batch 的唯一 warehouse 绑定。

### 6.2 VAD 与内容哈希字段

增强后保留源片段和父录音血缘，但必须区分“当前音频身份”和“增强前来源身份”。

当前工程中 `original_audio_sha256`、`segment_pcm_sha256` 等可能被下游用作当前样本身份。不能把这些字段原样拷贝后声称是增强音频摘要；应依照现有契约更新对应当前内容字段，或将只属于源样本的字段迁移到 `augmentation.source_*` 中。

文件摘要与 PCM 内容摘要分别标明类型，不相互替代。没有重新计算对应 PCM 摘要时，不能把 WAV 文件 SHA 填入 `segment_pcm_sha256`。

VAD 父源区间保留为来源坐标，不再表示增强文件内的播放时长。首版不要求重新对齐原时间戳，也不能让下游把原区间直接用来裁剪增强文件。

### 6.3 文本与既有计算结果

- 人工金标的文字内容可继承，明确标记为 `inherited_from_source`，不是对增强音频重新完成人工标注。
- 原始 ASR 文本和模型信息保留为来源证据，建议置于增强来源命名空间；不得保留原 ASR completed 状态使下游误以为已对增强音频跑过识别。
- 原 DNSMOS、SNR、语速、VAD、时间对齐、自动声学标签等与原音频绑定的结果归档为来源信息，不能作为增强音频的有效评分。
- 原语义判断和自由 tag 的计算记录可归档；无明确继承规则时不直接当成对新音频完成的新判定。
- 训练禁用标记、人工使用限制、许可证/来源约束、既有 train/val/test 划分及防泄漏分组必须保留。
- 本流水线不自动重新划分数据集；源样本与增强样本共享来源分组，不因生成新 id 而进入不同训练/验证/测试集合。
- lineage 追加增强处理记录，同时能够追溯原始 id、batch 和音频，不丢失上游血缘。

## 7. 产物与整批完成定义

建议产物根目录：

```text
datasets/stage1/augmented/<source_batch>/tempo_<factor_tag>_<recipe_digest>/
  manifest.parquet           # 全批完成后发布的增强样本 Manifest
  audio/<hash_prefix>/*.wav   # 增强音频，分散目录
  results.parquet            # 覆盖每条输入的处理明细
  recipe.json                # 冻结输入、倍率、算法、版本和参数
  summary.json               # 总数、成功/失败、缓存、时长、耗时等
```

`factor_tag` 是规范倍率的可读形式，精确身份由 recipe_digest 保证。若现有目录规范要求调整，保持阶段化落点与 batch/倍率/配方隔离。

要求：

1. 原始数据只读；生成文件使用新的路径和原子写入，失败时不会出现指向半成品的成功记录。
2. 正常全批成功时，输入 N 条，增强 Manifest 也是 N 条；每个源 id 恰好映射一个增强 id。
3. `results.parquet` 必须覆盖全部 N 条输入，记录源 id、计划增强 id、status、输出路径、错误代码/信息、耗时、缓存命中等。
4. 若成功 M 条、失败 F 条，则 `N=M+F`；缓存命中包含在成功中，不重复计数。失败行不能被无声丢弃。
5. 允许保留成功部分为 `manifest.partial.parquet` 供恢复与诊断，但 F 大于 0 时不得发布成“整批完成”的正式 `manifest.parquet`，运行终态必须明确为 partial/failed，并对调用者返回失败状态。
6. 全部补跑成功后再原子发布正式 Manifest；临时清单、结果报告、正式发布状态保持一致。
7. 同指纹重复运行可幂等复用；不同输入快照、倍率或算法版本进入不同配方目录，不能覆盖旧配方。
8. 原 batch 原样本仍在上游，增强 Manifest 默认不掺入原音频，不把失败样本的原路径当作增强成功输出。
9. 正式 Manifest 保持输入相对顺序，恢复和分片合并后也一致；results 通过源 id 明确对应。

## 8. 并发、分片与运行记录

复用现有线程/进程执行器和自动 split → run → merge，不要求用户手工执行三条分片命令。

- 首版建议线程池调度有界 FFmpeg 子进程；每个任务最多启动一个处理子进程，内部线程数默认限制为 1 或显式小值。
- 计算实际总并发：活动分片数 × 每片 worker 数 × 后端内部线程数。不能只展示 workers 而忽略分片和后端线程。
- 设置 `max_in_flight`，按批读取和提交；不得为整批百万行一次性创建 Future 或载入全部音频波形。
- 音频文件流式处理或按单条生命周期加载，结果及时落盘；大文件处理有明确的内存与超时边界。
- 以 CPU、磁盘吞吐及内存预算选择 workers；不固定假设需要 GPU。
- 写入 runs、配置快照、输入快照指纹、检查点及日志；展示总条数、已完成、失败、缓存命中、待处理、输入输出总时长、处理速度和耗时。
- 每条失败可定位到源 id、路径和具体阶段。错误日志适量截断，避免无限累计 FFmpeg stderr。
- 中断时停止派发，有限等待或终止在途子进程，保留已提交结果和可恢复状态。

首版不要求本地百万条压测或固定吞吐承诺，但必须通过小批可控任务证明并发实际生效且不突破预算。

## 9. 缓存、恢复与异常处理

### 9.1 缓存身份

至少纳入源 batch、源 sample_id、所选输入 key、**实际输入音频内容摘要**、精确归一化倍率、算法/后端版本、滤镜链、声道策略、输出采样率/编码和算子版本。

不能只用 Sample 的旧 sha256、音频文件名、原 completed 状态或粗略倍率后缀判断命中。输入文件路径不变但内容改变时必须失效。

恢复当前输入快照的标签和金标时，缓存只复用有效音频处理结果并重新合并当前来源元数据，不能把旧缓存中的整份 labels 覆盖当前人工修订。整步检查点需同时覆盖本次冻结的 Manifest 元数据内容。

缓存命中前验证产物存在、可解码且摘要/关键参数相符；文件删除、损坏或被替换时自动重算，不能继续输出失效路径。

### 9.2 断点续跑

复用 `--resume <run目录>`，从原运行冻结的 batch、Manifest 和 speed_factor 恢复，不重新使用缺省 1.2 覆盖原倍率。

- 成功且产物有效的行直接复用。
- 未完成、失败、产物丢失或损坏的行重新处理。
- 失败检查点不能导致错误行永远跳过；最终整批完成检查依据全部源 id 的有效结果。
- 恢复时显式传入不同倍率或不同输入快照，应报指纹不匹配并要求开启新运行，不能向旧配方写入另一倍率结果。
- `--force` 绕过成功缓存进行重算，依然从原始输入音频开始，不对旧增强音频二次加速。
- 进程崩溃可能留下尚未提交的完整文件；允许校验后采用或重算，最终清单不能重复追加同一派生样本。

### 9.3 失败分类

全局配置或依赖错误在批量前终止；单条音频缺失、解码失败、处理超时、输出校验失败等记入 results，默认继续处理其他行以发现整批问题。

只对临时 I/O 或明确可恢复异常进行有限次重试；坏音频、非法参数和依赖缺失不盲目重试。失败最终必须影响整批完成状态，不能因 `fail_fast=false` 而宣称全部成功。

## 10. 建议交付结构与命令

建议短名 `augment_batch_speed`，保音高算子 `augmentation.tempo`。

- `src/audio_engine/core/augmentation/`：可复用保音高处理、参数校验、派生身份、来源证据处理与配方。
- `src/audio_engine/operators/augmentation/tempo.py`：算子与注册；优先复用既有原子文件、缓存和执行能力。
- `pipelines/augment_batch_speed.yaml`：正式生产入口，显式 output.manifest，配置增强和整批发布/报告步骤。
- `configs/augmentation/speed.yaml`：默认 speed_factor=1.2、保音高后端及运行参数。
- CLI/source_naming 的必要适配：batch 解析、`--speed-factor`、动态输出命名、子分片参数传递。
- 操作手册、针对性测试和 `单条流水线执行命令.txt` 更新。

不要求照搬模块拆分，但正式能力必须在公用库和注册算子中，不能只交付一个临时脚本。

预期命令如下，**speed-factor 及本流水线的动态命名是本需求待实现能力，不代表当前 CLI 已支持**：

```text
# 指定 batch，默认 1.2 倍，输入为该 batch 的片段快照

# 明确使用已入仓的整批快照；实际 input_audio_key 在配置中指定

```

运行日志必须打印实际输入快照、输入 audio key、生效倍率、保音高方式、并发参数和产物路径。示例命令中的 batch_A 为占位批次，操作者按实际命名替换。

## 11. 验收标准

### 11.1 批次与参数

- [ ] 一条命令指定 batch 完成整批增强；默认使用 1.2，不需要手工遍历文件。
- [ ] CLI 1.3 覆盖 YAML，YAML 自定义倍率不会被 CLI 默认值覆盖；所有分片使用同一生效参数。
- [ ] 非法倍率在预检拒绝；等价倍率身份一致，不同高精度倍率不会共用结果文件。
- [ ] 默认片段快照和显式仓库 Manifest 均可处理；不能串 batch、混阶段、随机抽样或按标签隐式过滤。
- [ ] 已增强输入不会在重复执行时被再次自动增强。

### 11.2 音频与身份

- [ ] 小型真实音频 fixture 验证 1.2/1.3 倍输出有效、时长约为 T/factor，采样率和声道保持；正常长度输入建议容差为 max(50ms, 3% × 理论时长)，实际后端偏差需报告。
- [ ] 用稳定单频/合成谐波信号验证主要频率基本保持，例如正常测试信号偏差不超过 2%；与改变音高的重采样结果可区分。
- [ ] 至少听验少量真实语音，确认语速提升、无明显升调、正文首尾未丢失；不能仅凭纯音测试宣称语音质量达标。
- [ ] 静音、短音频、多声道、中文/空格路径、缺失和损坏文件有针对性验证。
- [ ] 原音频、原 batch Manifest 未变化；新 id、当前内容摘要、音频路径和 duration 正确。
- [ ] 片段父源血缘可追溯；原 ASR/质量计算状态不会误绑定新音频，金标文本及训练禁用、防泄漏分组正确继承。

### 11.3 整批处理与恢复

- [ ] N 条正常输入生成 N 条增强样本，源 id 与增强 id 一一对应，分片和乱序完成不串样本、不打乱顺序。
- [ ] 注入单条失败后 results 仍覆盖 N 条，N=M+F；有失败时不发布整批完成正式清单。
- [ ] 中断恢复复用有效结果，补跑未完成/失败行；删除或破坏一个输出文件会触发该行重算。
- [ ] 修改倍率、音频内容或后端版本后缓存失效；恢复时指纹不匹配不会混写旧产物。
- [ ] 同配方重复运行幂等，不额外复制一批样本；force 从源音频重新处理。
- [ ] 并发大于 1 确实生效，队列和后端进程数有界；日志/summary 展示真实成功、失败和耗时。

测试保持小而有效，不要求百万条本机压测或无关全仓库回归。FFmpeg、真实语音或目标服务器不可用时，明确记录未验证项，不用占位音频或 Mock 冒充真实增强验收。
