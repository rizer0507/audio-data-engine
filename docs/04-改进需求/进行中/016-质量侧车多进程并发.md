> 状态：**进行中（仅需求，未落地）**  
> 日期：2026-09-10  
> 触发：`pipelines/audio_quality_sidecar.yaml` 当前为串行单 worker，万级～十万级批次 DNSMOS 侧车成为 v3 分拣前瓶颈。  
> 前置 / 关联：引擎并发能力已由 [001-数据清洗并发改进](../已完成/001-数据清洗并发改进.md) 落地；侧车本身由 [012-B](../已完成/012-B-质量与分拣.md) / [009-噪声评分流水线接入](../已完成/009-噪声评分流水线接入.md) 落地；消费方为 [014](../已完成/014-分拣生产默认切换至v3.md) / [015](../已完成/015-v3分拣支持三族及以上.md) 的 `classify_dataset_v3`。分拣侧加速见 [017](./017-v3分拣加速.md)（并发待做）/ [019](../已完成/019-Levenshtein原生加速.md)（编辑距离已交付），与本需求正交。  
> 范围边界：只改质量侧车的**执行并发与可运维默认**；不改 DNSMOS 算法、阈值契约、`noise_risk` / `noise_band` 语义，也不改 classify 合并逻辑。

---

## 1. 当前事实（结论）

**不是多进程并发。**

`pipelines/audio_quality_sidecar.yaml` 现配置为：

```yaml
execution:
  executor: sequential
  workers: 1
  fail_fast: true
```

含义：

| 项 | 现状 |
| --- | --- |
| 执行器 | `sequential`（逐步、逐样本串行） |
| 并发度 | `workers: 1` |
| 引擎能力 | 框架已支持 `thread` / `process` + CLI `--workers/--executor`（见 001） |
| 侧车默认 | **未启用**上述并发；生产手册按默认 YAML 跑即串行 |

`quality.dnsmos` 用 `ClassVar` 持有单个 `DnsmosP835Session`（ONNX `InferenceSession`）。串行下安全；若直接开多线程共享同一 session，需额外验证线程安全或改为每 worker 独立 session。

---

## 2. 我想做什么

让 `audio_quality_sidecar` 在单机上**默认以多进程（或经验证安全的等价并发）跑 DNSMOS**，把侧车墙钟时间压下来，而不改分数语义与输出契约。

目标路径不变：

```text
cleaned_*（resampled_16k）
  → audio_quality_sidecar（本需求：并发跑 quality.dnsmos）
  → quality_sidecar_*（dnsmos_* / noise_band / noise_risk）
  → classify_dataset_v3（按 ID+原音频哈希合并）
```

优先方案（建议）：

1. **流水线默认改为 `executor: process`，`workers` 取可配置正整数**（例如 CPU 核数相关默认，或文档给出本机推荐值）。
2. 复用 001 已有进程池 / checkpoint / cache / fail 隔离；避免为侧车另起一套并行框架。
3. 保留 CLI 覆盖：`--executor sequential|thread|process`、`--workers N`，便于小批量调试与机器差异调参。
4. 若实测 Windows `spawn` + 每进程加载 ONNX 开销过大：允许「Manifest 分片 + 多进程 shard」作为同等验收路径（仍属 001 能力），但**默认一条 `pipeline run` 应可并发**。

备选（仅当进程池实测不如线程池时）：`executor: thread`，但必须保证每线程独立 ONNX session（或加锁且证明不拖垮吞吐），并写入验收说明。

## 3. 数据从哪来、结果要什么

- **输入**：清洗后的 `cleaned_<BATCH>.parquet`（`resampled_16k`，未 pad），与现侧车一致。
- **输出**：`quality_sidecar_<BATCH>.parquet`，字段与现契约一致：
  - `quality.dnsmos_sig / bak / ovrl`
  - `quality.dnsmos_status`（`success | failed | unsupported`）
  - `quality.dnsmos_model_digest` / `dnsmos_preprocess_version`
  - `noise_band` / `noise_risk`（未校准前可为 unknown / null）
- **规模**：典型批次数千～数万条；目标场景可到十万级。不清楚精确上限时，以「比串行明显加速且结果一致」验收。

---

## 4. 业务上有哪些规矩

1. **分数可复现**：同一模型文件 + 同一预处理版本下，并发与串行对同一样本的 `dnsmos_*` 在容差内一致（沿用 `configs/quality/dnsmos_p835.yaml` 的 `acceptance.score_atol`，默认 0.15）。
2. **失败隔离**：单条推理失败仍写 `status=failed`、风险 unknown，**禁止**写默认干净分；缺模型 / 缺 `onnxruntime` 启动失败语义不变。
3. **不改阈值与校准门禁**：`calibrated: false` 时行为与 012-B 一致；本需求不代替人工校准。
4. **顺序与血缘**：输出 Manifest 在 id / sha256 / quality 字段上与串行语义一致（顺序可按引擎既有并发约定复原）。
5. **资源可控**：默认 workers 不得无脑打满导致内存打爆（每进程一份 ONNX）；文档给出推荐区间与「内存不够就降 workers / 改分片」说明。
6. **手册与命令台账**：`单条流水线执行命令.txt`、local/dev 工序一手册中侧车命令注明默认并发，并给出串行对照命令（调试用）。

## 5. 我怎么才算满意

- [ ] `audio_quality_sidecar.yaml` 默认不再是 `sequential` + `workers: 1`（改为 `process` 或经验证的并发配置）。
- [ ] 同一小批（例如数百～一千条）串行 vs 并发：manifest 关键质量字段一致（在容差内），无半写文件、无 cache 损坏。
- [ ] 同机对比墙钟时间有可见加速（目标至少接近线性到 workers 中等规模，如 4～8；具体倍数写入实测表）。
- [ ] CLI `--workers` / `--executor` 可覆盖默认；`fail_fast` 行为符合现引擎语义。
- [ ] 缺模型时启动失败；单条失败不污染整批干净分。
- [ ] 手册 / 命令台账已更新；本需求完成后移入 `已完成/`。

## 6. 其他我想说的

- **不要重写 DNSMOS 算法**；只动执行并发与必要的 session 生命周期（每进程懒加载即可，与现 `ClassVar` 模式兼容）。
- 参考成功先例：清洗流水线 `data_cleaning_source_A.yaml` 的分步 `execution`；ASR batch 的 `thread` 配置。DNSMOS 偏 CPU + ONNX，**优先试 process**。
- Windows 上注意 001 已记录的 spawn / 序列化开销：若 `process` 反而更慢，在需求验收里写明并切换到「thread + 独立 session」或「run-shards」。
- 与 014/015 的关系：侧车加速直接服务 v3 默认分拣路径，但不阻塞 014/015 的契约切换。
