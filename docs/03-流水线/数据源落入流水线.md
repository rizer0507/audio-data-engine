# 数据源落入流水线构建

> 日期：2026-08-20
>
> 定位：**工序一（数据清洗落库打标）的前置环节**。外部已有物理音频，经本流水线登记后，成为本工程内的「逻辑数据源」，才能投入 [数据清洗流水线](./数据清洗流水线.md)。对齐见 [工序总览](../01-项目架构/工序总览.md)。

## 核心原则：工程内只有逻辑资产

本工程 **不持有、不搬迁、不复制** 任何 wav / pcm 等物理文件。

| 层级 | 在哪里 | 本工程是否管理 |
|------|--------|----------------|
| **物理资产** | 工程外部（NAS / 盘阵 / 共享盘 / 供应商交付目录等） | 否，只读引用 |
| **逻辑资产** | 本工程 `resources/`（及后续流水线产出的 manifest） | 是，唯一真相 |

```text
外部物理目录（本工程之外）
    │  只读引用 path，不拷贝进仓库
    ▼
┌──────────────────────────────────────┐
│         数据源落入流水线               │
│  （本工程只产出逻辑资产）              │
│                                      │
│  1. 确认外部物理路径可读               │
│  2. 扫描外部路径 → 样本级逻辑索引      │
│  3. 登记到 resources/manifest.yaml    │
│  4. 形成体系内「数据源 X」             │
└──────────────────────────────────────┘
    │
    ▼
数据源 X（逻辑） → 数据清洗流水线 → 标注流水线 → 训练集（均为逻辑产物）
```

下游所有 Pipeline 输入的都是 **已登记的逻辑数据源**（`source_id`），运行时再按登记的 `path` 去读外部物理文件。

字段与登记规范见 [数据源登记规范](../02-规范规则/数据源登记规范.md)。

---

## Step 1：确认外部物理路径

物理文件已经存在于工程外某处，本步骤只确认：

- 路径可访问（权限、挂载、网络盘在线）
- 本批数据边界清晰（不要把两批混在同一引用根上）
- **不**把文件拷进 `audio-data-engine/`，也 **不**要求仓库内出现 `data/batches/` 之类物理目录

示例（路径仅作登记，不表示文件归本仓所有）：

```text
# 外部，本仓不管理
D:/SharedAudio/vendor_20260815/     ← 供应商交付，物理所在
\\\\nas\\audio\\outbound_batch_b\   ← 另一批，物理所在
```

---

## Step 2：扫描外部路径 → 样本级逻辑索引（可选但推荐）

对登记的 `path` 做 **只读扫描**，生成样本级逻辑索引。索引里只存元数据与指向外部文件的指针，**不落地音频副本**。

| 字段 | 说明 |
|------|------|
| `id` | 文件名 stem |
| `filename` | 文件名 |
| `path` | **外部**绝对路径（指向物理文件） |
| `sha256` | 可选；用于去重 / cache key |
| `format` / `sample_rate` / `channels` / `duration` | 可选 probe 信息 |
| `broken` | probe 失败时标记，不删除物理文件 |

索引产物也是逻辑资产，例如：

```text
resources/
├── manifest.yaml                 ← 数据源总清单（必有）
└── sources/
    └── source_A/
        └── samples.jsonl         ← 样本级逻辑索引（推荐）
```

单条示例：

```json
{
  "id": "000001",
  "source_id": "source_A",
  "filename": "000001.wav",
  "path": "D:/SharedAudio/vendor_20260815/000001.wav",
  "sha256": "89f2a3...",
  "format": "wav",
  "sample_rate": 8000,
  "channels": 1,
  "duration": 4.72,
  "broken": false
}
```

校验失败只打标记，物理文件原样留在外部。

## Step 3：登记逻辑数据源

在 `resources/manifest.yaml` 追加一条记录，完成本工程内的「落入」：

```yaml
sources:
  - source_id: source_A
    source_name: 数据源A
    ingested_at: "2026-08-20T10:30:00+08:00"
    origin: "某供应商-第一批客服外呼录音"
    path: "D:/SharedAudio/vendor_20260815"   # 外部物理根路径，仅引用
    format: wav
    sample_rate: 8000
    file_count: 15000
    note: "8k 单声道；样本索引见 resources/sources/source_A/samples.jsonl"
```

**登记完成 = 体系内逻辑资产「数据源 A」已形成。**  
此后工程内只认 `source_id`，不认裸物理目录。

---

## Step 4：交付下游（逻辑引用）

| 本工程交付物 | 性质 | 作用 |
|--------------|------|------|
| `resources/manifest.yaml` 中一条 `source_*` | 逻辑 | 数据源唯一入口：名称、落入时间、外部 path |
| `resources/sources/source_*/samples.jsonl`（若有） | 逻辑 | 样本级索引，path 仍指向外部 |

下游清洗流水线：

```yaml
name: data_cleaning_source_A
input:
  source: source_A    # 逻辑数据源，非物理目录
```

解析链：

```text
source_A
  → resources/manifest.yaml 取 path / 元数据
  → （可选）samples.jsonl 取逐条外部 path
  → 运行时只读打开外部物理文件
  → 清洗结果仍写为逻辑 manifest（parquet/jsonl），不回写物理资产到本仓
```

## 完整流程

```text
外部物理音频（已存在，本仓不持有）
        │
        ▼
Step 1  确认外部 path 可读（不拷贝、不入库物理文件）
        │
        ▼
Step 2  只读扫描 → 样本级逻辑索引（可选）
        │
        ▼
Step 3  写入 resources/manifest.yaml → 形成「数据源 X」
        │
        ▼
Step 4  下游以 source_id 引用逻辑资产 → 清洗 / 标注
```

两批数据 = 两条逻辑登记，互不混用：

```text
外部目录 A  ──落入──▶  数据源 A（逻辑）──▶ 清洗 A
外部目录 B  ──落入──▶  数据源 B（逻辑）──▶ 清洗 B
```

---

## 注意事项

1. **本仓零物理音频**：仓库内不出现 wav/pcm 资产目录设计；`path` 一律指向工程外
2. **落入 = 登记逻辑资产**：不是「把文件搬进工程」
3. **source_id 唯一**：`resources/manifest.yaml` 内不可重复
4. **先落入再清洗**：清洗流水线只接受已登记的 `source_id`
5. **Git 只追踪逻辑资产**：`resources/manifest.yaml` 及样本索引纳入版本管理；物理文件不进 Git
6. **外部 path 变更**：只改 manifest 中的 `path`（及索引中的指针），不涉及本仓文件迁移
