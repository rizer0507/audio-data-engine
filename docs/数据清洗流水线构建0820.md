# 数据清洗流水线

Manifest 为唯一真相源，Pipeline YAML 编排 Operator DAG，支持断点续跑与 cache。

**前置条件**：原始 wav / pcm 须先通过 [批次资产入库](./构建思路.md#二数据批次资产从物理文件到可引用数据源) 登记为 **数据源**（如 `数据源A`）。清洗与标注流水线的输入均为数据源 manifest，而非直接扫描 raw 目录。

```text
物理文件 batch_A  →  batch ingest  →  数据源 A  →  数据清洗流水线  →  cleaned_source_A
物理文件 batch_B  →  batch ingest  →  数据源 B  →  数据清洗流水线  →  cleaned_source_B
```

## A. 数据清洗流水线（只做音频质量，不做标注决策）

### 目标

- 输入：**数据源**（如 `source_A` / `数据源A`），即 `datasets/sources/source_A.yaml` 指向的批次 manifest
- 输出：`datasets/manifests/cleaned_source_A_YYYYMMDD.parquet`

### 流程

1. **前置：批次入库（batch ingest，在清洗流水线之外执行）**
  - 扫描 `data/batches/batch_A/` 下 wav / pcm
  - 写入 `datasets/batches/batch_A/manifest.parquet` + `batch_meta.yaml`（含入库时间、来源）
  - 注册 `datasets/sources/source_A.yaml` → 形成 **数据源 A**
2. **标准化**
  - 从数据源 manifest 读取样本，`id` = 文件名 stem；`sha256` 用于去重与 cache key
  - pcm 先经 `audio.pcm_to_wav` 转码（配置 sample_rate / channels）
3. **重采样**
  - `audio.resample` 统一到 16k（输出 key：`resampled_16k`）
4. **质量检测**
  - 损坏：`probe_audio` 失败 → `labels.broken = true`
  - 空白：`duration == 0`（输入已是 VAD 后片段，流水线不再跑 `audio.vad`）
  - `quality.filter` 标记 `labels.audio_pass`
5. **导出清洗结果**
  - 仅保留 `audio_pass == true` 样本进入 `cleaned_source_A_YYYYMMDD.parquet`
  - manifest 继承 `batch_id`、`source_id`、`ingested_at`、`origin` 血缘字段



### YAML（已落地）

见 `pipelines/data_cleaning_source_A.yaml`：

```yaml
name: data_cleaning_source_A

input:
  source: source_A                              # 解析 resources/manifest.yaml

output:
  manifest: datasets/manifests/cleaned_source_A.parquet

pipeline:
  - { name: ingest, operator: ingest.scan }     # 仅当尚无样本索引时真正扫盘
  - operator: audio.pcm_to_wav
    params: { sample_rate: 8000, input_audio_key: raw, output_audio_key: pcm_wav }
  - operator: audio.resample
    params: { sample_rate: 16000, input_audio_key: pcm_wav, output_audio_key: resampled_16k }
  - operator: quality.probe
    params: { input_audio_key: resampled_16k }  # labels.broken
  - operator: quality.filter
    params: { expr: "label_broken != True and duration > 0", label_key: audio_pass }
  - operator: quality.select
    params: { expr: "label_audio_pass == True" }  # 只保留通过样本写入 output
```

运行：

```bash
# 1. 先在 resources/manifest.yaml 登记 source_A（path 指向外部物理目录）
# 2. 执行清洗
audio-data pipeline run pipelines/data_cleaning_source_A.yaml
```

数据源 B 同理，复制为 `data_cleaning_source_B.yaml`，改 `input.source` 与 `output.manifest` 即可。

### 大数据量并发执行

样本级并发在**步骤内部**进行，`ingest.scan`、`quality.filter`、`quality.select` 这类批量算子始终串行（它们本身已是整表操作）。并发度在 YAML 的 `execution` 里配置，也可用 CLI 临时覆盖：

```bash
# 单进程多线程（10 万条以内首选）
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --workers 8

# 关闭并发做对照基线
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --executor sequential

# 进程池仅在 GIL 卡死时试；当前清洗链路默认 thread 更快
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --executor process --workers 4
```

长任务默认每 1000 条落一个 checkpoint，中断后可从同一 run 目录续跑（已完成的步骤整步恢复，被打断的步骤只补做剩余批次）：

```bash
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --resume runs/<run_id>

# 不需要断点续跑时可关掉，省约 20% 开销
audio-data pipeline run pipelines/data_cleaning_source_A.yaml --checkpoint-every 0
```

10 万～20 万条建议再叠加 Manifest 分片，多进程并行：

```bash
# 默认稳定哈希；时长差异大且已有 duration 时用 --strategy duration-balanced
audio-data manifest shard datasets/batches/batch_A/manifest.parquet \
  --shards 16 --output-dir datasets/shards/source_A

audio-data pipeline run-shards pipelines/data_cleaning_source_A.yaml \
  --shard-dir datasets/shards/source_A --parallel-shards 4 --workers 8

audio-data manifest merge "runs/<run_root>/shard-*.parquet" \
  --output datasets/manifests/cleaned_source_A.parquet --expected-shards 16
```

分片模式崩溃后，重复执行同一条 `run-shards` 命令即可续跑。被强杀的进程会在 cache / derived 留下 `*.tmp*` 孤儿文件（不影响正确性），用 `audio-data pipeline clean-temp <pipeline.yaml>` 清理。

并发的正确性保证、实测吞吐与调参建议见 [并发改进方案](./数据清洗流水线并发改进方案0820.md)。
