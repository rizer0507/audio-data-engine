# 全自动训练与评测闭环改造方案

## 1. 结论

当前项目已经具备一个可靠的**样本级执行引擎**，但还不是一个完整的**任务级编排系统**。
`PipelineRunner`、分片、checkpoint、operator cache、Manifest 和文本指标引擎解决了“一个 YAML
怎样稳定处理一批样本”；尚未解决的是“一个数据版本怎样自动经过清洗、伪标注、审核、拆分、
训练、候选模型注册、回归评测和发布门禁”。因此继续增加一次性合并脚本，只会把人工操作从一个
XLSX 转移到另一个 XLSX，而不会形成自动化闭环。

建议把项目目标明确为两条可复现的顶层任务：

```text
build-and-train(dataset_release, training_recipe)
build-and-evaluate(dataset_release, candidate_model, baseline_model)
```

两条任务共享同一套数据版本、Gold、拆分结果、模型注册表和评测口径。Parquet Manifest 是唯一
真相源；XLSX 只作为人工审核的导入/导出视图，不再作为流水线之间的接口。

---

## 2. 当前框架的能力盘点

### 2.1 已经具备、应该保留的能力

1. **统一样本结构**：`Sample` 已包含音频资产、多个模型转写、质量指标、标签、血缘、状态和错误，
   足以承载后续自动分类与评测。
2. **可恢复执行**：步骤 checkpoint 会校验输入内容、operator 版本和参数，流水线也支持分片运行、
   并行 shard、失败 shard 重跑和确定性合并。
3. **模型推理解耦已经起步**：Qwen、SenseVoice、Kimi 可以独立产出 Manifest；
   `quality.aggregate_manifests` 会严格检查 ID 集合，避免静默错配。
4. **指标实现方向正确**：Gold production 的 agreement CER 与 evaluation CER 已共用 MetricRunner，
   只通过 profile 配置 reference/hypothesis，避免两份 CER 实现漂移。
5. **运行产物可追溯**：每个 pipeline run 会保留实际配置、manifest、metrics、checkpoint 和日志。

### 2.2 关键缺口

| 缺口 | 当前表现 | 直接后果 |
|---|---|---|
| 顶层编排 | `stages:` 只能顺序调用若干 YAML，缺少任务依赖、条件、审批和产物契约 | 每个阶段仍需人工启动和找路径 |
| 数据版本 | 文件名带 `source_name`，但没有不可变 release ID 与 catalog | 同名文件可能被覆盖，无法回答模型训练用了哪批数据 |
| 自动分拣 | 只有通用 filter/select，业务规则仍在 XLSX 和脚本中 | Gold/hardcase/noise 口径不可审计、不可复现 |
| 人工审核闭环 | 没有 review queue、标注状态和导入冲突检查 | 每次靠人工复制列，容易漏样本或串版本 |
| 数据集拆分 | `sample_test_set.py` 按文件名抽样 | 规则硬编码，且可能发生说话人/会话泄漏 |
| 训练集导出 | `build_training_set.yaml` 仍是示例，输入和 `gold_text` 契约不完整 | 无法可靠触发外部训练框架 |
| 训练集成 | 没有 training job、状态、日志、模型产物和指标契约 | 训练完成后仍需人工搬运 checkpoint |
| 评测闭环 | `asr_eval.yaml` 假设 old/new 文本已经在 Manifest 中 | 新旧模型推理、聚合、评测与报告仍靠手工串联 |
| 汇总指标 | MetricRunner 主要写逐条 quality 字段 | 缺少 corpus CER、分桶指标、置信区间和回归门禁 |
| 产物发现 | scripts 接受任意 XLSX/Parquet 路径 | 操作者必须反复寻找“正确的那一个文件” |

### 2.3 当前设计中的具体风险

- `multi_asr_aggregate.yaml` 的名字容易造成误解：它现在只做聚合，不再执行 Qwen、SenseVoice 或
  指标。若操作手册仍把它描述为“一条命令跑完所有模型”，实际行为会与预期不一致。
- `aggregate_manifests` 以 `id` 为唯一 join key。不同来源可能产生相同文件 stem；即使 ID 集合恰好
  一致，也需要同时核验 `sha256`，否则可能把文本挂到错误音频。
- 当前聚合要求所有模型 ID 完全一致。这适合严格评测，但不适合生产推理中的部分失败。生产场景
  应支持 `strict` 和 `left` 两种策略，并显式输出 missing/failed 原因；评测发布前再强制 strict。
- `quality.filter` 在表达式异常时会把整个 chunk 标为未通过并继续运行。清洗 exploratory run 可以
  这么做，但 Gold、train/eval release 应当 fail fast，避免悄悄生成空数据集。
- `quality.text_metrics` 每个样本、每个 comparison 都写一条 INFO 日志，十万到百万条数据会制造
  大量日志并影响吞吐；应改为分批计数和周期性进度。
- Gold agreement 目前以 Qwen 为 pseudo-reference，只能表示模型间一致性，不能被命名为真实字准率。
  仅在人工确认的 `gold_text` 上计算的指标才可用于模型质量结论。
- 多个 scripts 重复实现归一化、编辑距离、XLSX 合并和列名约定，会产生口径漂移。尤其
  `SequenceMatcher.ratio()` 与 Levenshtein CER 不是同一指标，不能混用同一个“字准率”名称。

## 3. 目标架构

### 3.1 四层职责

```text
Task Orchestrator（任务 DAG、审批、重试、状态、通知）
        ↓
Domain Pipelines（清洗 / 伪标注 / 分拣 / release / train / eval）
        ↓
Operators & Adapters（ASR、规则、采样、训练框架、模型推理、指标）
        ↓
Artifact Catalog（Manifest、数据 release、模型、报告、血缘）
```

当前 Pipeline Engine 保持为第二、三层的执行内核，不建议重写。第一层先实现轻量本地
orchestrator；当需要跨机器调度、定时运行和 Web UI 时，再把相同任务 DAG 映射到
Argo Workflows、Prefect 或 Airflow，而不是让业务逻辑依赖某个调度平台。

### 3.2 顶层任务 DAG

```text
ingest_and_clean
  └─ fan-out: qwen / sensevoice / kimi / ...
       └─ aggregate_and_score
            └─ classify
                 ├─ auto_gold ─┐
                 ├─ noise      ├─ review/import ─ dataset_release
                 └─ hardcase ──┘                    ├─ train ─ model_register
                                                   └─ eval inference
                                                        ├─ baseline
                                                        └─ candidate
                                                             ↓
                                                      aggregate_metrics
                                                             ↓
                                                       regression_gate
```

每个节点必须声明：输入 artifact 类型、输出 artifact 类型、参数摘要、代码版本、重试策略、完成条件。
节点只引用 catalog 中的 artifact ID，不能要求用户手填上一步生成的随机路径。

## 4. 核心数据契约

### 4.1 数据集 Release

建议增加 `DatasetRelease` 元数据文件：

```yaml
release_id: ds_20260901_mt3000_v001
parent_release_id: null
source_snapshot: cleaned_mt3000@sha256:...
policy_version: selection_zh_v1
normalization_version: zh_asr_v1
gold_revision: gold_20260901_01
split_seed: 20260901
group_key: conversation_id
outputs:
  train: artifacts/.../train.parquet
  dev: artifacts/.../dev.parquet
  test: artifacts/.../test.parquet
counts: {train: 0, dev: 0, test: 0, hardcase: 0, noise: 0}
created_at: ...
git_commit: ...
```

Release 一旦成功即不可修改；修订标注或规则必须生成新 release。训练与评测命令只接受
`release_id`，从根本上消除“到底用了哪个 XLSX”的问题。

### 4.2 Sample 需要补充的业务字段

建议保留 `Sample` 通用结构，并逐步加入有校验的字段约定：

- `source_dataset`、`source_batch`、`conversation_id`、`speaker_id`：来源和防泄漏分组；
- `annotation.state`：`unreviewed/auto_accepted/human_accepted/rejected/conflict`；
- `annotation.gold_text`、`annotator`、`revision`、`updated_at`；
- `classification.bucket`：`gold_candidate/hardcase/noise/voicemail/reject`；
- `classification.reason_codes`：机器可统计的原因数组，不能只留自然语言；
- `split`：`train/dev/test/holdout`，以及 `split_policy_version`；
- 每个 transcript 的 `model_id`、`model_version`、`decode_config_digest`、`prompt_digest`；
- `dataset_release_id` 与 `selection_policy_version`。

为了兼容现有 Parquet，可以先把 annotation/classification 放在 `labels` 中，但必须通过 schema
validator 检查必需字段；长期建议升级为显式的 Pydantic 子模型。

### 4.3 模型注册表

为外部训练框架增加最小 `ModelVersion` 契约：

```yaml
model_id: qwen_sft_mt3000_r001
base_model: qwen_asr_v1
training_release_id: ds_20260901_mt3000_v001
training_recipe: recipes/qwen_sft_v3.yaml
checkpoint_uri: /models/qwen_sft_mt3000_r001
git_commit: ...
status: ready
```

评测 pipeline 引用 `model_id`，由 adapter 解析 checkpoint 与推理配置，禁止把“new_model”固定成
某个目录或手工拷贝的列名。

## 5. 工序③：自动分拣与人工审核闭环

### 5.1 规则不应只有一个 85% 阈值

建议 `selection_policy.yaml` 配置化以下信号：

- 多模型 pairwise CER、一致模型数量、空文本数量；
- 音频时长、SNR、静音占比、VAD 语音占比；
- SenseVoice event/tag、串音/音乐/非人声检测；
- 强模型置信度、重复字符、异常长度比；
- 来源、业务场景和关键词覆盖；
- 是否已有人工标注及标注 revision。

推荐的决策顺序：

1. 音频损坏、全静音、明确非人声 → `reject/noise`；
2. 至少两个独立模型高度一致，且强模型置信度和音频质量达标 → `auto_gold`；
3. 模型分歧、否定词/数字/实体差异、低置信度 → `hardcase`；
4. 其他样本 → `review_queue`，不能默认进入 Gold。

每条决策必须输出 `bucket`、`reason_codes`、`policy_version` 和所有使用的阈值。阈值应先在一批
人工确认样本上校准，衡量 auto-gold precision；不能把“模型间 85% 一致”直接当作 Gold 正确率。

### 5.2 人工审核接口

短期无需立即开发 Web UI，可以实现可逆的两步命令：

```bash
audio-data review export --queue <artifact_id> --output review.xlsx
audio-data review import --queue <artifact_id> --input review.xlsx
```

导出表必须带只读的 `sample_id`、`sha256`、`queue_id`、`revision`；导入时校验四者，拒绝重复 ID、
未知 ID、音频 hash 变化、旧 revision 覆盖新 revision。人工只编辑 `decision`、`gold_text`、
`reason`。导入结果写回新的 annotation artifact，不原地修改原 Manifest。

中期可接 Label Studio 或内部标注平台，但仍沿用同一 import/export contract。

### 5.3 可复现拆分

拆分必须在 Gold 确认之后执行，并以 `speaker_id` 或 `conversation_id` 分组，避免同一人/同一通对话
同时出现在 train 和 test。策略需固定随机种子，并支持：

- 固定永不参与训练的 `holdout`；
- 按来源、时长、噪声类型、hardcase 类型分层；
- 历史 release 的 test 集保持稳定；
- 按音频 `sha256` 去重，而不只是按 `id`；
- 输出 train/dev/test 的交集检查和分布报告。

## 6. 工序④：对接外部训练框架

不要把另一套训练框架的内部逻辑搬进数据引擎。增加一个窄的 `TrainingAdapter`：

```text
prepare(release_id, recipe) -> training_input artifact
submit(training_input) -> job_id
status(job_id) -> queued/running/succeeded/failed
collect(job_id) -> ModelVersion
```

第一版 adapter 可以只是受控的 subprocess/SSH 命令，但必须：

- 将 release manifest 导出成训练框架要求的 JSONL/SCP；
- 保存实际 recipe、环境、git commit、依赖版本与 stdout/stderr；
- 支持幂等 job key：`release_digest + recipe_digest + code_commit`；
- 明确成功标志和 checkpoint 路径，不能以“进程退出了”代替模型可用；
- 训练后自动注册 `ModelVersion`，并触发 smoke inference；
- 训练失败只重试可重试错误，OOM 等错误应带诊断终止。

数据引擎与训练框架之间的接口只包括不可变训练输入、job 状态和模型产物。这样两套代码库可独立
发布，同时顶层任务仍可一键执行。

## 7. 工序⑤：自动评测与增益判断

评测任务应接收：

```text
evaluation_release_id + candidate_model_id + baseline_model_id + eval_profile
```

然后自动完成：

1. 校验评测集含人工确认 `gold_text`，且与 candidate 的 training release 无泄漏；
2. baseline 与 candidate 分别推理，产出独立 transcript Manifest；
3. 按 `sample_id + sha256` 聚合，并检查缺失、额外、失败和重复；
4. 用统一 normalization 与 MetricRunner 计算逐条编辑操作；
5. 计算 **corpus CER**（总编辑数 / 总参考字符数），不要只平均逐条 CER；
6. 按来源、时长、噪声、bucket、关键词、说话人属性等分桶；
7. 对 candidate-baseline 做 paired bootstrap 置信区间；
8. 输出 machine-readable `evaluation.json`、Parquet 明细和面向审核的 HTML/XLSX 报告；
9. 执行 regression gate，并决定 `pass/fail/needs_review`。

示例门禁：

```yaml
gates:
  - metric: corpus_cer
    condition: candidate <= baseline - 0.003
  - metric: hardcase_cer
    condition: candidate <= baseline
  - metric: critical_keyword_recall
    condition: candidate >= baseline
  - metric: inference_failure_rate
    condition: candidate <= 0.001
```

“总 CER 有增益”不能掩盖关键子集退化。报告至少展示总量、分桶、失败率、比 baseline 变好/变差
的样本数，以及最大回归 badcases。

## 8. 命令与产物发现体验

最终建议把常用操作收敛为：

```bash
# 数据准备到可审核队列
audio-data task run prepare-release --source mt3000 --policy selection_zh_v1

# 人工审核完成后冻结数据版本
audio-data release create --from-task <task_id>

# 构建训练集并调用外部框架
audio-data task run train --release ds_... --recipe qwen_sft_v3

# 新旧模型完整评测并执行门禁
audio-data task run evaluate --release ds_eval_... \
  --candidate qwen_sft_mt3000_r001 --baseline qwen_asr_v1

# 不找文件，只查 ID
audio-data task status <task_id>
audio-data artifact show <artifact_id>
audio-data report open <evaluation_id>
```

所有任务生成固定结构：

```text
runs/tasks/<task_id>/
  task.yaml                 # 解析后的完整参数
  state.json                # 节点状态与时间
  events.jsonl              # 状态事件
  nodes/<node_id>/...       # 原有 pipeline run 目录
  outputs.json              # artifact IDs，而不是临时路径列表
```

失败后执行同一个 task ID 即从成功节点继续；参数变化则生成新 task ID，避免误复用旧 checkpoint。

## 9. 分阶段实施计划

### P0：停止结果继续散落（1～2 周）

1. 定义 `ArtifactRecord`、`DatasetRelease`、`ModelVersion` 三个 schema；先用本地 JSONL catalog。
2. 为 pipeline 输出注册 artifact ID，并实现 `artifact list/show/path`。
3. 聚合 join 增加 `sha256` 校验和对齐报告。
4. 统一 scripts 使用 MetricRunner/normalizer；标记旧 XLSX 合并脚本 deprecated。
5. 修正文档：明确 aggregate 只聚合，metric 单独执行。

**验收**：操作者只提供 source/release/model ID，不再寻找上一步 XLSX 或 Parquet 路径。

### P1：完成数据集生产闭环（2～4 周）

1. 实现配置化 `quality.classify` 与 reason codes。
2. 实现 review queue export/import 及 revision/hash 校验。
3. 实现 group-aware、stratified、deterministic split。
4. 冻结 release，生成质量报告、统计和 train/dev/test manifests。

**验收**：除真正需要人工听审的队列外，从清洗结果到 dataset release 一条任务完成；重复运行得到
相同拆分和相同 release digest。

### P2：训练接入（2～3 周）

1. 确认外部训练框架的输入、提交、状态、产物协议。
2. 实现一个 adapter、job registry、日志收集和模型注册。
3. 增加训练 smoke test 与失败恢复。

**验收**：`task run train` 最终返回可被 ASR operator 消费的 `model_id`。

### P3：评测与回归门禁（2～4 周）

1. 参数化模型 operator，使 pipeline 接受 model registry 引用。
2. 完成 baseline/candidate fan-out、严格聚合和 corpus 汇总。
3. 增加分桶、paired bootstrap、HTML 报告和 gate。

**验收**：一个 model ID 自动得到与固定 baseline 的可复现报告和 pass/fail 结论。

### P4：服务化（按需要）

在本地 task DAG 和 artifact contract 稳定后，再接入调度平台、对象存储、数据库、Web UI、通知和
权限控制。不要把选择规则、指标计算或 release 语义写进调度平台专有 DAG。

---

## 10. 优先级与非目标

最高优先级不是新增更多 ASR 模型，也不是开发大而全的 UI，而是：

1. **不可变 release + artifact catalog**；
2. **自动分类规则 + 可逆人工审核**；
3. **训练/模型 adapter contract**；
4. **端到端评测与门禁**。

短期不建议：

- 用 XLSX 作为主数据库；
- 把所有阶段塞进一个超长 YAML；
- 让数据引擎直接依赖训练框架内部 Python API；
- 在没有人工校准集的情况下自动接受所有“模型一致”样本；
- 同时引入数据库、消息队列、Airflow 和标注 Web UI。

先用文件型 catalog 和本地任务状态把数据契约跑通，可最小成本消除当前最痛的“手工执行、寻找
文件、重复合并、口径不一”；之后扩展到多机调度时，不需要推倒现有 Pipeline Engine。
