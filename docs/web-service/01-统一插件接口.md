# 01｜流水线与 tag 的统一插件接口

日期：2026-10-19。状态：待实现。前置：[00 总需求](00-总需求与实施顺序.md)。

## 1. 目标

流水线与 tag 必须共用一套插件契约、目录发现和生命周期入口。HTTP、Worker、前端依赖统一契约，不依赖某条流水线名称或某个 tag ID。

插件化不能只有一个 `plugins/` 文件夹或元数据列表；必须贯通“发现 → 校验 → 规划 → 冻结 → 执行 → 结果追溯”。现有引擎保持业务执行职责，插件层负责适配。

## 2. 最小插件分类与身份

- `kind=pipeline`：执行已登记 YAML 流水线、生产 DAG 或评测流水线。
- `kind=tag`：一条可独立选择的 tag 定义，一个 tag 内可以有多条规则。
- `adapter`：实现插件生命周期的技术适配器，例如 `yaml_pipeline`、`production_pipeline`、`tag_definition`。

插件稳定引用为 `(kind, id, version)`，版本全部使用字符串。tag 插件的 `id` 直接沿用 `tag_id`，version 沿用现有定义版本，不能复制生成另一套 tag 身份。流水线 id 优先沿用现有 YAML name，version 由插件登记明确给出。

`api_version` 是统一接口版本，与业务插件 version 分开；本期为 `"1"`。同一目录 generation 内不允许同 kind/id 注册多个相互覆盖的当前定义；本期不建设多版本安装器，历史版本通过任务快照展示，是否可执行还要验证对应实现是否存在。

ID 必须可稳定用于 URL 和文件映射，限制为字母、数字、下划线、短横线及合法点号；禁止路径分隔符和 `..` 路径片段。文件命名与旧 tag 规则一致。

## 3. 统一契约

在 `audio_engine.plugins.contracts` 定义可校验、可序列化的契约。以下签名是目标，不要求已有引擎类直接继承：

```python
class Plugin(Protocol):
    def describe(self) -> PluginDescriptor: ...
    def validate(self, request: PluginRequest, context: PluginContext) -> ValidationReport: ...
    def plan(self, request: PluginRequest, context: PluginContext) -> ExecutionPlan: ...
    def execute(self, plan: ExecutionPlan, context: PluginContext) -> PluginResult: ...
```

`describe/validate/plan` 不执行 ASR、声学推理、写样本结果、安装依赖或启动外部服务。允许读取定义、元数据、已存在产物和必要文件属性。真实模型连接测试和输入检查通过明确的后端操作执行，不隐式藏在插件目录查看中。

### 3.1 PluginDescriptor

必须包含：

- `kind/id/version/api_version`，中文名称和业务描述。
- `adapter`、`status`（enabled/disabled/archived）、`runnable` 和不可执行原因。
- `input_kinds`：支持 `source`、`dataset` 中哪些输入。
- `output_kinds`：可能产生的 manifest、report、annotation_package 等产物类型。
- `parameters_schema`：JSON Schema，带中文标题、说明、默认值、范围、必填、枚举。
- `capabilities`：可执行能力和限制，包含 `supports_resume`、`supports_cancel`、`supports_tag_selection`、`purpose`（processing/tagging/evaluation）。
- `dependencies`：声明的算子、模型角色、tag、证据能力、配置与文件引用；运行期再展开实际选中依赖。
- `definition_digest`、`implementation_digest`、`catalog_generation`、可定位定义来源。

tag 详情还要提供业务定义、规则、三态示例、片段/词表引用及声学需求。流水线详情提供实际步骤或 DAG 节点和依赖。目录级 `runnable` 只表示适配器及定义可用，不等价于当前服务器已完成运行条件检查。

### 3.2 PluginRequest

包含：插件引用、输入引用、参数、模型绑定、选中 tag 引用、执行选项。

- 输入使用后端生成并返回的 source_id 或 dataset/artifact ID，页面由 batch/路径选择器解析引用，不要求用户手填内部 ID；不能由浏览器传任意服务器命令或任意输出路径。
- 模型绑定按 `route_id` 指向后端生成的 `connection_id`，页面按显示名称和地址选择；同模型家族不同路次可以绑定不同端口，连接可跨 batch 复用。
- tag 必须显式给出 id/version；空列表表示不额外选择 tag，不得解释为全库。打标任务要求至少选择一个 tag。
- 执行选项只包含已定义的并发、证据模式等安全字段；不能接受任意 env、Python import、shell command 或脚本路径。
- 所有参数在后端按 schema 校验，未知字段默认拒绝；内部生成的输出和凭据配置不作为可任意改写的表单字段。

任务可以是 `task_type=pipeline` 或 `task_type=tagging`。前者有一个 root pipeline，可绑定显式 tags；后者通过同一注册表解析 tags，再由 tag 执行协调器组批。协调器只负责集合调度，不是另一套业务插件接口。

HTTP 与插件层使用同一个任务请求外壳，规范字段为 `task_type/root_plugin/input/parameters/model_bindings/tags/execution`。例如：

```json
{
  "task_type": "pipeline",
  "root_plugin": {
    "kind": "pipeline",
    "id": "audio_ingest_vad_asr_dnsmos_tags",
    "version": "1"
  },
  "input": {"kind": "source", "source_id": "src_8a253e1f"},
  "parameters": {},
  "model_bindings": [
    {"route_id": "qwen1", "connection_id": "conn_3f170d2a"}
  ],
  "tags": [
    {"kind": "tag", "id": "critical_short", "version": "1"}
  ],
  "execution": {"evidence_mode": "existing"}
}
```

示例展示程序生成的请求结构，其中 source_id 和 connection_id 均由登记 API 返回后自动填入，不是用户表单必填字段；不表示这个 source/连接已存在或所选 tag 在单路证据下必然命中。root schema 的参数放 parameters；通用执行选项放 execution，证据模式只在 execution 维护一份。适配器负责将这些选项写入任务私有有效配置。

`task_type=tagging` 时 root_plugin 为 null，input 必须是 dataset 引用，tags 非空；parameters 是该 tag 批次的已声明共享配置，不允许覆盖 tag_id/version 或规则正文。适配器单插件调用时，注册表将这一外壳解析为对应的 PluginRequest 视图；返回的总体计划保留原外壳及各插件子计划。

### 3.3 ValidationReport

包含 `ok`、`errors`、`warnings` 和标准错误项：`code/message/plugin_ref/field_path/definition_path/details`。

校验覆盖结构、接口版本、ID 与版本、依赖引用、schema、能力兼容、禁用/归档、参数边界和循环依赖。错误可以定位具体配置及字段。不得将失败依赖默认为成功。

对本次选择无关的插件异常，目录中保留诊断，其他合法插件仍可使用；全局索引重复、schema 损坏等无法形成一致目录的问题则拒绝刷新，保留旧 generation。

### 3.4 ExecutionPlan

必须包含：

- `plan_id/plan_digest`、插件引用、catalog generation 和完整规范化请求。
- 输入来源、已解析模型连接的非敏感字段、secret 引用、预期模型身份。
- 已解析节点、依赖顺序、模型路次、显式选中 tag 与证据依赖并集。
- 将复用/可能补算的证据、缺失条件、并发限制、恢复与取消支持。
- 任务专属输出路径模板、预期产物类型、预计步骤；样本数未知时明确未知。
- 完整定义快照：递归子流水线、算子参数、tag/rule、片段、词表正文、证据配置、归一化配置及其内容摘要。

规划不代表已计算，不得输出伪造的命中率、DNSMOS 分数或试跑结果。若成本估计没有依据，显示未估计。

### 3.5 PluginContext

只通过显式上下文提供：项目绝对根路径、任务及 attempt ID、任务工作目录、只读快照/产物解析、任务私有模型参数、secret 解析、取消令牌、进度上报与结构化日志接口。

业务执行使用任务上下文和快照，不读取随时变化的全局模型配置。禁止在 API 或共享 Worker 进程内修改全局 `os.environ` 来切换任务模型端口。旧代码需要环境变量时，在任务私有子进程及其子节点中传独立 env。

### 3.6 PluginResult

包含 `outcome`（succeeded/failed/cancelled）、实际产物引用、实际 run 目录引用、计数/指标、告警、结构化错误、子节点结果和使用的快照摘要。

tag 批执行结果必须保留逐样本、逐规则的 matched/not_matched/unknown、证据状态、缺失依赖与命中来源；可使用现有产物文件承载明细，不能将全量明细塞入任务数据库或单个 API 响应。

只有预期必需产物完成校验和注册后，才能报告 succeeded。部分样本失败按插件明确策略记录真实计数；关键节点失败不能仅因进程返回 0 就报告整体成功。

## 4. 注册、发现与配置

### 4.1 唯一目录入口

`configs/plugins.yaml` 为流水线登记和 tag 库发现入口。示意格式：

```yaml
api_version: "1"
extension_modules: []
pipelines:
  - id: audio_ingest_vad_asr_dnsmos_tags
    version: "1"
    adapter: production_pipeline
    name: 入库、切段、多路识别、质量评分与标签
    definition: pipelines/audio_ingest_vad_asr_dnsmos_tags.yaml
    status: enabled
    purpose: processing
    supports_tag_selection: true
    parameters_schema:
      type: object
      additionalProperties: false
      properties: {}
tag_libraries:
  - path: configs/tagging/library
    runtime_config: configs/tagging/zh_asr_free_tags_v2.yaml
```

这是目录字段示例，不是完整可运行主链配置。实际 input_kinds、模型角色、参数映射和能力由适配器声明并验证，不得仅靠目录里手写 true 冒充已实现能力。

tag 的 id/version/status/规则直接由 `load_tag_library` 读取，不在插件清单中再次逐条登记。下划线开头示例文件继续跳过。发现后由 `tag_definition` 适配器生成统一 descriptor。已存在的 runtime_config 作为证据与词表上下文；本次任务的 select_tags 在任务私有快照中生成，不修改原配置。

流水线清单可内联轻量 schema 或引用 schema 文件；已有算子、处理参数和 DAG 只在原 YAML 中维护。不能把普通 YAML 参数原样全量暴露为浏览器可修改字段，适配器应限定可覆盖项及映射。

首批登记至少覆盖现行生产主链、独立 GLM ASR、独立 Qwen ASR、DNSMOS、自由标签、现有评测及所需导出能力。优先适配已有 `pipelines/` 文件；没有合适导出封装时，按现有算子接口补最小流水线，而不是在 HTTP 路由里写特殊全量导出实现。

每项必须声明实际前置输入：例如独立 ASR 流水线需要已具有相应音频资产 key 的 Manifest 时，应限制 dataset 输入并校验资产，不把原始目录直接塞入假定已清洗的 pipeline。首期不需要将所有历史 YAML 自动开放；只有登记、校验并完成适配的定义可执行，历史实验配置保留原状。

### 4.2 技术适配器注册

在统一注册表提供 `register_adapter(adapter_id, factory)`。内置适配器只注册一次。

- `yaml_pipeline`：复用 PipelineRunner 与现有 CLI 的输入/路次/分片等解析能力。
- `production_pipeline`：复用 ProductionOrchestrator，补齐任务隔离、环境传递、取消和恢复。
- `tag_definition`：复用 TagLibrary、TaggingConfig、TaggingService。

新增技术执行方式可由 `extension_modules` 引用本仓库受信模块，在启动/刷新时注册工厂。浏览器不能传入模块名、上传可执行代码或安装任意包。适配器运行时在 API 与 Worker 中必须使用相同加载入口。

不同 adapter 的工厂选择属于注册表职责；API、Worker、页面不能出现按 `audio_ingest...`、`critical_short` 等业务 ID 的 if/elif 分发。

### 4.3 刷新语义

- 启动加载目录，管理员通过统一刷新操作原子生成新 generation。
- API 每次查询返回 generation；任务提交需要确认当前定义摘要，发生变化返回 409 并要求重新规划。
- Worker 执行已冻结快照，不依赖自己进程中的“最新目录”；新增扩展模块需要加载时，在任务隔离子进程使用相同入口，并校验实现摘要。
- 新增定义刷新后对新任务可见，已排队与运行任务继续使用旧快照。
- 被停用插件不允许新任务选择，历史结果可读。已排队任务使用其冻结状态；若管理员需阻止执行，明确取消该任务。

### 4.4 用户手动启用与归档

pipeline 与 tag 共用 `set_status(kind, id, status, expected_revision)` 管理入口，经统一 API 暴露。页面主操作只提供 enabled（启用/在用）和 archived（归档），允许 archived → enabled 恢复。兼容既有 disabled 状态，但不要求用户维护第三个常用分类，也不偷偷将旧 disabled 自动转换为 enabled。

- 流水线 status 写回 `configs/plugins.yaml` 的对应条目；tag status 写回其原定义 YAML，沿用现有 enabled/archived 标志映射，不在插件清单复制 tag 状态。
- 跨进程锁、revision/CAS 与原子替换避免丢更新，重复设置相同状态保持幂等。持久化前校验；文件与目录 generation 的切换需保持一致，不能返回成功后刷新又恢复旧状态。
- 管理状态不改变插件 id、业务 version、规则或词表；只更新管理修订、目录 generation 与必要的目录摘要。不触发 ASR/声学推理、不提交重算任务、不删除证据缓存。
- archived 从新任务默认可选列表排除，可在“归档”页签查看和重新启用。后端拒绝新计划/新提交选中归档插件，不能仅靠前端隐藏按钮。
- 旧计划尚未提交时发生归档，提交应返回 409 并要求重新选择；已入队或运行任务继续使用冻结快照，不因当前归档被中断。恢复原 job 的兼容 attempt 沿用快照；新建 rerun job 需验证当前可选状态，已归档时提示先重新启用。
- 状态校验覆盖显式选中的 tag 及已登记插件依赖；不得在根流水线仍为 enabled 时悄悄运行其已归档的依赖，也不能静默跳过该步骤。声明的插件依赖失效时给出定位原因；纯内部 YAML/算子节点仍按其执行契约处理。
- 归档不会移除已经写入样本的标签、人工记录或历史产物；旧结果可读，历史状态按当时快照展示。恢复启用不自动恢复到所有任务的选择列表。

状态管理与 runnable 分开：enabled 只表示用户归为在用，不保证依赖或模型在线；依赖损坏时可持久化状态但必须保留不可执行诊断，不能宣称已可运行。

## 5. 执行适配的关键约束

### 5.1 普通流水线与生产 DAG

不能直接读取原 YAML 后调用最底层 runner 而跳过现有 CLI 对 source_name、source_dir、input_manifest、asr_run、sharding、输出命名的处理。

优先提取现有参数解析和执行服务供 CLI/插件共享；必要时允许插件在独立子进程中使用参数数组调用现有 CLI，禁止 shell 字符串。子进程必须读取冻结配置、写入任务专属目录、上报真实 run 信息，不得扫描全局“最新 run”猜测结果。

生产主链保留 ingest → VAD → ASR 与 DNSMOS 并行 → join → tag 的实际依赖关系。仅选择一条 ASR 路次时不得强行生成其他模型路次；节点参数和每条 route 的连接绑定要写入冻结配置。

### 5.2 tag 的插件执行

每个 tag 独立描述、选择、校验与追溯，但多选 tag 必须合并成同一有效 TaggingConfig，由一个批次执行协调器复用 TaggingService。共享证据按音频内容身份、模型、能力、参数摘要去重，不能因同时选两个 tag 重复推理。

公共生命周期中，单 tag 的 execute 可以委托同一组批协调器；批执行仍使用统一 PluginRequest/ExecutionPlan/PluginResult，不另建一套不兼容的 tags-only 任务协议。

- `existing`：只读已存在证据，不调用 ASR 或声学模型，缺证据为 unknown。
- `compute_acoustic`：仅补所选规则实际需要的声学证据，不自动补跑 ASR；纯文本 tag 不要求声学依赖。
- `plan/preview`：只规划，不补算。需要真实样本预览结果时提交明确的 preview 任务，使用相同插件执行链并标记不发布正式结果。
- 多 tag 可重叠；同 tag 多规则命中去重但保留逐规则来源。
- 沿用 NOT unknown = unknown；缺失、失败、成功空文本、清洗后为空不得混同。
- 自动重判、规则更新、局部重跑不得清空人工添加、屏蔽及范围外结果。
- 自由标签依赖独立 evidence_config，不将旧五类队列、selection_config 或唯一 risk subtype 重新作为全局门禁。

流水线 `supports_tag_selection=false` 时传入 tags 要报错，不能悄悄忽略；true 时由适配器将选择注入原生 tagging 节点，或在声明的最终节点后执行一次 tag 批处理，不能同一次任务重复打标。

### 5.3 新算法边界

组合已有能力新增 tag 不需要修改 Python。全新算法允许新增底层证据能力或算子代码，并遵循已有算子/能力契约，补齐版本、依赖和测试；新增执行后端通过 register_adapter 接入。不得承诺全新算法只写 YAML 即可实现，也不得为每条新业务规则增加 Web 特判。

## 6. 快照、版本、恢复与缓存

任务提交时冻结实际内容及递归依赖，而不是只存源文件路径和哈希。冻结后所有配置引用必须指向快照副本或已验证的不可变产物，执行阶段不能悄悄回读原词表/子 YAML。

实现摘要要能识别工作区未提交源码变化，不能只记录 Git HEAD；至少覆盖实际适配器、相关算子与证据能力实现及声明的实现依赖。密钥只存引用，不进入快照正文、计划摘要展示或日志。

恢复要求输入身份、参数、规则/依赖内容、实现和模型身份兼容。源文件已更新但完整旧快照与兼容实现仍可用时，允许按旧快照恢复；缺旧内容或代码不兼容则拒绝混用，提供创建新任务。不得用“同版本号”掩盖内容改变。

改变业务阈值应使相关 tag 判定缓存失效，但同音频、模型、能力和评分参数不变的声学证据可复用。改变音频、模型身份或评分参数必须使对应证据缓存失效。

模型服务仅能验证 `/v1/models` 等返回的公开身份时，明确身份保证范围；用户替换同名权重需要更新连接的 model_revision，不能宣称已校验远端权重文件内容。

## 7. 统一管理接口

HTTP 路由见 02；开发者命令至少提供以下等价功能，并调用同一注册表：

```text
python -m audio_engine.plugins list
python -m audio_engine.plugins show --kind pipeline --id <id>
python -m audio_engine.plugins validate --request <request.json>
python -m audio_engine.plugins plan --request <request.json>
```

示例 request 文件不含密钥。列出、查看、校验、规划在没有 GPU、vLLM 或声学模型时仍能使用，并据实返回缺失的运行条件；不因为一个无关插件缺依赖导致整个目录无法打开。

## 8. 验收

1. 新增一个复用现有算子的合法 YAML 流水线，只加定义与插件登记，刷新后能列出、生成表单、规划和执行，不改 API/Worker/页面。
2. 从 `_example_new_tag.yaml` 复制一个适用于固定证据样本的 tag，合法改名并填充规则，刷新后可见；只有显式选择时才参与任务。
3. 两个 tag 共享同一声学证据时一次补算，纯文本 tag 零声学调用，existing 与 plan 零推理调用。
4. ID/版本冲突、非法 schema、未知适配器、循环依赖、tag 文件名不符、缺词表、版本不匹配均有定位错误。
5. 快照能还原所用定义和词表正文；排队后修改源文件不影响旧任务；实现漂移不能静默恢复。
6. 与现有固定证据基线比较三态、来源、人工标签及片段身份保持一致；故意修复的原缺陷单独列出。
7. 目录加载不会启动模型，不要求安装未选插件的重型运行依赖；适配器异常不会变成“成功空结果”。
8. pipeline 和 tag 都能通过同一管理接口启用/归档并在重启后保留；重复操作幂等、并发冲突不丢状态。归档拦截新提交，已提交任务不受影响，恢复启用不改业务版本/规则，也不触发推理或清空历史标签。

交付插件接入说明，给出“新增流水线”“新增 tag”“新增处理算子/适配器”三个最小示例，说明哪些文件要改、哪些核心文件无需改。
