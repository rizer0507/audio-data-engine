# 00｜Web 服务总需求与实施顺序

日期：2026-10-19。状态：待实现。项目：`D:/Work/audio-data-engine`。

## 1. 背景与目标

当前主要依赖命令行、YAML 和临时脚本执行音频数据处理。目标是在现有引擎上提供完整网页入口，日常通过页面完成数据源登记、模型连接配置、流水线选择、tag 选择、任务执行、结果查看和导出。

流水线与 tag 库必须作为插件存在，共用注册、发现、描述、校验、规划、执行和版本追溯接口。以后新增已有能力组合的流水线或 tag，增加配置并接入统一接口即可，前端、API 和任务 Worker 不再逐个适配业务名称。

## 2. 用户负责的前提与服务负责的边界

- 用户提供服务器上真实存在、服务进程有读取权限的数据源路径。
- 用户自行启动 GLM 或 Qwen 的 vLLM 服务，并提供实际访问地址、端口和服务模型名。
- Web 服务负责检查输入、准确传递地址端口与模型参数、调用真实处理能力并展示真实结果。
- Web 服务不管理外部 vLLM 的启动、重启、GPU 回收或进程生命周期；取消任务不得停止外部 vLLM。
- VAD、DNSMOS 等本地能力仍复用现有实现，其运行依赖按所选插件实际需求检查。缺少依赖须具体说明，不能假设两个 vLLM 端口就能满足整条生产主链。
- 允许只运行 GLM、只运行 Qwen，或按需求配置 N 路 ASR。不得隐藏要求固定三族六路；某个特定规则依赖缺失时按该规则契约返回 unknown 或阻止该能力执行。

## 3. 当前仓库基线

初次编写时 Web 骨架中的源码、配置和测试文件为空；当前已有后续实现时应复核现状并增量修改，不覆盖已有代码。现有可复用能力包括：

- `core/registry.py` 的 `OperatorRegistry`，以及 `core/operator.py` 的算子契约。
- `core/pipeline.py` 的 `PipelineConfig`、`PipelineRunner`。
- `core/production/` 的生产 DAG 编排，现行主链 YAML 为 `pipelines/audio_ingest_vad_asr_dnsmos_tags.yaml`。
- `core/tagging/library.py` 的定义库、选择校验和定义快照；`core/tagging/service.py` 的 `TaggingService`。
- `configs/tagging/library/` 的一 tag 一文件定义，以及自由标签 v2 的独立 evidence 配置。
- `core/catalog.py`、`core/artifacts.py`、现有 Manifest、审核、Gold 和评测能力。

现有 `core/stage1/adapters/` 和部分脚本包含启动 vLLM 的代码。不得直接将这些模型启动流程作为 Web 任务入口。当前生产编排也不能直接认定满足 Web 的取消、隔离输出和恢复要求，必须完成适配和验证。

工作区存在其他未提交修改。开始前查看 `git status`，不覆盖、不回滚、不顺手清理这些修改。

## 4. 第一版功能范围

### 4.1 必须交付

1. 数据源通过 batch 和服务器实际路径登记、列表、修改和检查；source_id 自动生成，用户不用填写。
2. GLM/Qwen 模型连接登记、修改、模型名检查、可选真实短音频试转写；connection_id 自动生成，与具体 batch 解耦，可跨批次复用。
3. 插件目录：流水线与 tag 的列表、详情、版本、依赖、参数说明、启用状态和诊断；提供“启用 / 归档”按钮，由用户分类在用项与归档项。
4. 从插件选择生成任务表单，支持单独流水线、单独 tag 集合，以及声明支持 tag 后处理的流水线。
5. 独立 Worker 执行，支持状态、分阶段进度、增量日志、取消、恢复和重新运行。
6. 真实产物浏览、样本分页、转写和标签解释、音频试听、按现有协议审核与导出。
7. 经插件接口发起评测，展示实际指标、样本范围、失败样本和正式 Gold 门禁结果。
8. 插件扩展说明、接口测试、浏览器验收及服务器真实小批次验收记录。

### 4.2 本期不扩展

本期按单服务器、受控内网、单操作者管理台实现，不建设账号权限平台、分布式队列、容器调度平台、可视化 DAG 编辑器、在线 Python 编辑执行器、插件商店或训练平台。保留现有训练接口，不把外部训练集成作为本期验收条件。

插件安装及新增算法仍通过代码或配置文件完成。页面负责查看、选择、校验、刷新插件目录、任务级参数配置，以及启用/归档管理状态；[最新版 06](06-tag与流水线详情弹窗及编辑.md) 的详情弹窗只允许编辑解释文字，并显示最近修改时间，不编辑规则/参数。其他页面已有的任务参数配置与状态按钮继续保留。

## 5. 最小技术与进程结构

- 前端：React、TypeScript、Vite，复用当前 `frontend/` 骨架。
- HTTP：FastAPI；统一 `/api/v1` 前缀。
- 执行：独立 Worker，默认同时执行 1 个 Web 任务；单个任务内部仍可有受限并发与生产 DAG 并行。
- 持久化：本机磁盘上的 SQLite 保存任务管理信息；音频和业务样本继续使用文件系统、Manifest 与 Parquet。
- 部署：前端构建后由 FastAPI 托管，浏览器同源访问；开发时 Vite 代理 `/api`。
- 第一版使用状态及增量日志轮询，无需 WebSocket、Redis、Celery、PostgreSQL 或额外 Node 后端。

处理链：页面选择插件和输入 → API 校验并冻结计划 → SQLite 入队 → Worker 原子领取 → 插件适配器调用现有引擎 → 注册实际产物 → 页面读取状态与结果。

## 6. 在空骨架上追加的必要文件

保留已有目录，只为统一插件接入追加：

```text
src/audio_engine/plugins/
  __init__.py
  contracts.py             # 契约、元数据、请求、计划、结果、上下文
  registry.py              # 适配器注册、定义发现、校验、目录刷新
  adapters.py              # YAML 流水线、生产 DAG、tag 定义适配
  __main__.py              # 同一接口的开发者 list/show/validate/plan 命令
configs/plugins.yaml       # 流水线登记、tag 库路径、受信扩展模块
src/audio_engine/web/api/plugins.py
frontend/src/pages/Plugins.tsx
tests/test_plugins.py
```

实现时允许按实际复杂度将适配器拆成少量文件，但不得预先生成多层空目录、通用仓储框架或多套平行注册系统。原有 `web/services/engine.py` 负责调用插件接口，不再承担按流水线名称分发的逻辑。

## 7. 数据与配置权威来源

- 数据源：`resources/manifest.yaml` 为唯一登记来源，SQLite 不复制维护第二套数据源主数据。
- 模型连接：`configs/web.yaml` 为唯一连接配置来源；API key 使用环境变量引用，API 和日志不返回密钥。
- 流水线业务定义：沿用 `pipelines/` 及其被引用配置。
- tag 业务定义：沿用 `configs/tagging/library/`，片段、词表、证据配置沿用现有配置入口。
- 插件目录：`configs/plugins.yaml` 保存元数据和来源引用，不复制流水线 DAG、tag 规则或词表正文。
- 任务状态：SQLite；执行日志、不可变配置快照、断点与产物：`runs/` 和现有产物目录。

source_id、connection_id 是系统内部稳定引用，登记时自动生成，修改显示名、batch、路径或连接参数时不自动重建 ID；历史人工维护的 ID 保留兼容。页面使用 batch、路径或模型显示名供选择，ID 最多在高级详情只读展示。batch 必须单独保留并传给现有引擎的 source_name 参数，不能用自动 source_id 替代业务批次名。

插件管理状态写回唯一来源：流水线写 `configs/plugins.yaml` 对应条目的 status，tag 写原定义文件的 status。用户从页面切换后重启/刷新仍有效，不另建一套覆盖状态表。归档不删除定义、旧任务快照、人工标签或产物，也不终止已提交任务。

任务产物必须隔离。新任务或全量重跑不得覆盖同批次已有成功产物；适配器为现有执行器提供任务专属输出路径，沿用其 lineage 和产物注册机制。旧产物仍可按原路径或 artifact ID 读取。

## 8. 插件与兼容性原则

统一的是插件生命周期和数据契约，流水线、tag 的执行粒度与业务语义仍由适配器保留。

- 流水线通过适配器复用已有执行器，不新建第二个 DAG 引擎。
- tag 规则通过适配器复用 `TaggingService` 和现有条件语义；多个 tag 组批执行并共享证据，不能逐个 tag 重跑 ASR/DNSMOS。
- 新增 YAML 流水线并登记，或新增合法 tag 定义文件后刷新，即可出现在页面。目录发现不等于自动启用到已有任务。
- 新增处理算法优先走现有算子注册接口；新增执行后端通过统一插件适配器注册。不得增加业务名称对应的 API 路由。
- 旧 CLI 和旧 YAML 调用继续可用。CLI 中现有受支持参数映射需复用或提取，避免 Web 和 CLI 两套不一致的路径、命名与参数重写逻辑。
- 保持自由标签与旧互斥分拣解耦；unknown、人工标签来源、片段 ID、父源血缘和正式 Gold 门禁不能因 Web 化改变。

## 9. 分阶段交付

### 阶段一：统一插件接口

实现 01 的契约、注册、目录、冻结和现有执行器适配；离线扩展与兼容验收通过。未具备的适配能力显示为不可执行，不能先挂空壳宣称已支持。

### 阶段二：真实后端与任务执行

实现 02 的配置管理、插件 API、入队、隔离执行、状态恢复与基础产物读取。使用自动化测试的本地 HTTP 测试服务验证端口和协议映射；明确这些测试不等于真实 vLLM 验收。

### 阶段三：前端操作台

实现 03 全部页面并接入真实 API；没有后端支持的操作应明确不可用，不能用固定数组填满页面冒充真实接入。

### 阶段四：结果、审核与评测闭环

完成样本筛选、试听、解释、人工操作、导出和评测插件。处理结果版本与人工状态冲突，验证正式 Gold 门禁。

### 阶段五：联调、部署与验收

按 04 完成回归、扩展验收、浏览器流程和服务器小批次真实试跑。未获得服务器路径、端口或运行依赖时继续完成可独立验证部分，将真实环境条目标为待验证。

## 10. 总验收条件

用户配置真实数据源与已启动的模型地址后，可以在页面完成“选择流水线与 tag → 提交 → 看进度日志 → 查看真实音频与结果 → 筛选导出”，无需为每次任务修改脚本。

新增一个复用现有算子的流水线插件，以及一个组合已有能力的 tag 插件后，只修改定义和登记，刷新目录即可使用，API、Worker、前端源代码不变。任务配置与依赖有完整快照，任务恢复不会混入新定义，取消不会停止用户 vLLM，历史产物和人工记录不丢失。
